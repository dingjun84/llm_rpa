## T1 ⚠️ 收紧姓名匹配：把「包含即可」换回「逐字精确」+ 明确的消歧规则

**优先级最高。这是唯一一处「为了先跑通而明知故犯」的地方。**

### 现状（2026-09-17 起，临时）

- 实现：`crates/automation-core/src/policy.rs::ContainsNameMatcher`
- 开关：`RuntimeConfig.relaxed_name_match`（界面「宽松姓名匹配（⚠️ 临时措施）」，**默认开**）
- 装配点：`apps/desktop/src-tauri/src/runtime.rs::build_matcher`（**只影响真实模式**）
- 违反的约定：`docs/architecture.md` §6.4 / §6.6「姓名默认逐字精确匹配」

**当初为什么开**：OCR 把会话列表左侧的头像/未读红点按行并进了姓名块，
实测把「李四」读成 `0 李四`。逐字精确匹配对这种噪声零容忍，
于是整条链路卡死在「找联系人」，后面的点击联系人、标题核验、填入输入框**全都验证不到**。
操作者要求「先不用精确匹配，只要识别到包含的字符就行，先测试通过」。

### 现在的行为（放宽到哪、在哪里停住）

| 环节 | 是否放宽 |
|---|---|
| 精确匹配命中 | **不放宽**，原样返回 |
| 精确匹配报**歧义**（多个逐字相同 / 候选太近） | **不放宽**，直接拒绝、不降级 |
| 一个都没匹配上 | 放宽：候选文字**包含**目标名即算命中 |
| 包含命中多个 | 取**最短**的那个 |
| 最短的仍有并列（长度相同） | **不放宽**，按歧义拒绝 |
| 空目标名 | **不放宽**，直接拒绝（`contains("")` 恒为真，放任它等于「随便点一个」） |
| 低置信度候选 | **不放宽**，照旧过滤 |

### 已知的误判风险（**这些就是将来要修的**）

1. **两个联系人名字有重合字段。**
   例：列表里同时有「李四」和「李四杰」。两者都包含「李四」，
   而「李四」（2 字）比「李四杰」（3 字）短 ⇒ 会**选中「李四」**。
   目标若是「李四杰」，就点错了人。长度相同时才会拒绝。

2. **目标名出现在别人的消息预览里。**
   例：群「测试群一」里有人叫李四发了消息，该行预览读作
   `李四：可以了，登录进去了` —— 它**包含**「李四」。
   实测这条与真正的姓名行 `李四` 同时出现在候选区里，靠「取最短」才选中了姓名行。
   但如果目标名较长（例如「顺邦科技物流-Yuri」），而预览行更短，就可能反过来选错。

3. **联系人列表里的消息预览可能整段包含目标名。**
   单聊行的预览是最后一条消息的内容；那条消息本身就可能写着对方的名字。

4. 「最短」只是**在已知数据上成立**的启发式，没有任何保证。

### 收紧方向（按推荐顺序）

1. **先修 OCR，让放宽层根本不需要。**
   已知有效的手段：把窗口调大（字变大）、`winocr --upscale` 提高倍数、
   把 `contact_panel` 左边界挪到头像列右侧（默认已改成 `0.14`）。
   如果联系人区能稳定读出**干净的姓名行**，直接关掉这个开关即可。
   ⚠️ 但**不要**把「关掉开关」当成终点——见第 4 条。

2. **把「任意位置包含」改成「行首匹配」。**
   姓名行以姓名开头（允许前面有短噪声），预览行不是。
   这能一次性干掉风险 2 和 3，且比 `contains` 严格得多。

3. **用行结构消歧，而不是用长度。**
   姓名行与消息预览行在**字号、行高、y 间距**上不同；
   而且姓名永远是某一行的**第一行**。用 `TextBox::bounds` 的高度/位置判定，
   比「谁更短」有依据得多。

4. **收紧到「归一化全等」。**
   去掉非名字字符（头像碎片、未读数字、分隔符）后再比全等，
   而不是无界包含。风险 1 会因此消失（「李四杰」归一化后仍不等于「李四」）。

5. **若确实需要模糊匹配，用有界编辑距离 + 阈值**，
   并且**必须**在拒绝时给出「最接近的几个候选是什么、差多少」，
   而不是笼统地说「找不到」。当前架构明确禁止无阈值模糊匹配，所以这一步要先改架构文档。

6. **双重确认要变成硬要求。**
   现在联系人区命中后会用 `chat_header` 再核验一次姓名。
   收紧后应当要求**两处都命中且一致**才算通过，而不是「标题不符才报错」。

### 验收标准（做到这些才算 T1 关闭）

- [ ] `ContainsNameMatcher` 与 `RuntimeConfig.relaxed_name_match` **从代码里删除**
      （不是默认关掉——留着就迟早有人打开）。

- [ ] 风险 1–3 各有一条**失败用例**（构造出这些候选，断言**拒绝**而不是猜）。
- [ ] 用真实微信靶标跑通一次「找联系人 → 点击 → 标题核验 → 填入输入框」全流程，
      且 `relaxed_name_match = false`。

⚠️ **`ContactMatcher::accepts` 不要一起删**。它是「判据单一来源」的正解（见 T7），

## T2 四个区域的标定值会随窗口尺寸失效

`contact_panel` 的左边界（`0.14`）是在「窗口宽 960 / 974」下量出来的，
而会话列表左侧的导航图标栏与头像列是**固定像素宽**、不随窗口等比缩放。
实测姓名文字起点：896 宽时 x≈126、960 宽时 x≈140
⇒ 安全比例区间只有 **0.135–0.146**，余量 ±5px。

窗口尺寸一变，四个区域都要重标（不只是左边界）。

**2026-09-19 已缓解一半**：`ensure_calibrated_size` 现在会**自动把窗口调回标定尺寸**
（调不动才转人工），所以"窗口被拖动过 / 被别的程序改了大小"不再需要人工干预，
也不会拿错的标定去点。

**仍然存在的问题**：想**换一个**窗口尺寸（比如换了显示器、想用更大的窗口）就必须
重标四个区域 + 重记窗口尺寸，一次都不能省。根因是区域只按比例表达，
而真实界面不是等比缩放的。

**方向**：让区域支持「锚边 + 像素尺寸」的表达（例如「左边界 = 窗口左 + 130px」），
比例不变的部分保持比例、固定像素的部分保持像素，换尺寸就不必重标。
细节见 `.workbuddy-ai/memory/REFERENCE.md` §13。

**另一件待观察的事**：自动调完窗口后**没有等客户端重排完**就往下走了
（理由见 `docs/architecture.md`「标定尺寸」一节）。若真机上出现"第一帧是半画的"
症状，就在 `ensure_calibrated_size` 返回前补一次两帧一致的等待（复用 `wait_for_settle`）。

## T5 `min_confidence` 在真实模式下拦不住任何东西

`Windows.Media.Ocr` 不提供逐词置信度，`tools/winocr` 统一输出 `confidence = 1.0`。
所以「最低置信度」这道闸门形同虚设。需要真正的置信度门控就得换本地引擎
（例如 PaddleOCR）。**在换掉之前，不要以为低置信度会被拦住。**

## T7 ✅ 已修：同一条判据曾写在两个地方（「匹配器放宽了，任务照样转人工」）

**症状**：`ContainsNameMatcher` 已经接上生产装配点，端到端用例仍然报
`AMBIGUOUS_VISION：候选人文字「0 外部测试联系人」与目标「外部测试联系人」不完全一致`。

**根因**：编排层 `crates/automation-core/src/runner.rs::execute` 里**自己写了一套判据**，
与匹配器完全无关，两处都是**逐字相等**：

| 位置 | 原来的写法 |
|---|---|
| 「核验候选人」 | `matched.text.trim() != task.external_contact_name.trim()` |
| 「核验聊天页标题」 | `Ok(found) if found.text.trim() == task.external_contact_name.trim()` |

于是匹配器换了策略，这两道复检照样把结果挡回去。**最坑的是失败文案**——
「不完全一致」读起来像是 OCR 认不准，排查会一路往识别精度上找，
永远找不到「两道关卡各写了一套判据」这个真原因。

**修法**：给 `ContactMatcher` 加 `accepts(expected_name, candidate) -> bool`，
两处复检一律问匹配器。三个实现者各自实现：严格 = 逐字相等（**含别名表**，
原来复检连别名都不认）、放宽 = 包含、替身 = 委托内层。

### 由此确立的约定（**以后必须守**）

- 编排层**不得**自己判断「文字是否等于目标名」。凡是「这个候选行不行」的判断，
  一律走 `ContactMatcher`。
- 匹配器提供**两类**方法：`find_unique_exact_match` 负责「在候选集里挑一个」，
  `accepts` 负责「这一个行不行」。**两者必须对同一个名字给出同样的答案**——
  有用例（`a_dirty_name_still_finds_the_contact_under_relaxed_matching`）
  同时跑放宽层与严格层两组对照来钉住这一点。
- **一般化**：同一个判据出现在两个地方，就一定会有一天不一致。
  看到 `!=` / `==` 比较「目标值」时，先问「这是不是别处已经定义过的判据」。

## T9 模板匹配用的是纯 Rust 实现，不是 OpenCV

**现状**：`crates/vision/src/template.rs` 自己实现了归一化互相关
（等价 OpenCV 的 `TM_CCOEFF_NORMED`）：逐通道、多通道取平均、
按行分块并行（标准库 `std::thread`，不引 rayon）。

**为什么不用 OpenCV**：

1. **构建成本**：本机没有 OpenCV，`pkg-config` / vcpkg / 环境变量全都没有。
   要走 `opencv` crate 就得先装一套 C++ 构建链，而这是一个"双击就能跑"的桌面应用，
   发布路径上多一个原生依赖就多一处可能失败的地方；
2. **本地优先**：不联网、不注入、不 Hook 是这个项目的硬约束。少一个原生依赖，
   依赖清单就短一截，审计起来更清楚；
3. **算法本身不长**：NCC 的定义式只有十几行，真正的工程量在边界处理与
   与定义式的一致性上——这部分用纯 Rust 写反而更容易测（有两条用例把
   生产实现与定义式**逐位置**对比）。

**性能实测**（debug 构建，`measure_a_realistic_navigation_strip` 用例）：
导航条 73×734 + 26×26 模板，单次匹配 **346ms**（优化前 957ms）。
这个量级对"每次任务开始时跑一次"是可以接受的，所以没有进一步优化。

**什么时候该换成 OpenCV**：如果以后要在**整窗**上做模板匹配，
或者模板/搜索区大一个数量级，纯 Rust 的实现会变成秒级。那时再换——
`IconLocator` 这个端口就是为这一刻准备的，换实现不用动调用方。

## T12 界面标定出来的坐标没走服务端校验（`calibration::mark` 还没接命令）

### 修法：原来写的方案是错的，改成了纯校验命令

**原方案**（加 `mark_area` / `unmark_area` 两个**写配置**的命令，
界面改成调它们而不是改草稿）**不成立**，写在这里免得以后有人再走一遍：

界面的保存模型是**草稿式**的——拖框只改前端 `draft`，点「保存配置」才落盘，
`dirty` 标记与「保存」按钮都依赖这一点。若拖一下就调 `apply_mark` 直接写
服务端配置，会**绕过草稿**：用户拖一个框配置已经变了，按钮却还亮着
"有未保存的改动"，而"取消/不保存"这个动作根本无从实现。
当时写这条待办时没意识到保存模型是草稿式的，所以才把"接命令"当成了修法。

**实际采用的修法**（三处）：

1. `lib.rs` 新增 `validate_area_mark(key, rect)` 命令——**纯校验，不改状态**。
2. 界面在松手时调它：`RegionCanvas` 加 `onCommit`（拖动结束回调，

   `CalibrationPanel.commitRect` 拿它校验，不合法只提示、**不把框弹回去**
   （弹回去会让人以为拖动失灵了）。
3. `set_runtime_config` 落盘前**兜底再校验一遍** `area_marks`——
   界面那条路挡不住手改配置文件。

**判据仍只有一处**：两条校验都取自 `calibration`（`find_item` / `validate_rect`），
`lib.rs` 只是把它们串起来，没有另写一份。

**验收**：传一个不存在的 key 会被拒绝并说明原因；传一个越界的 rect 同样被拒。
✅ 已实测（临时 crate 里跑真依赖，4 passed / 0 failed）：
零尺寸矩形确实被拒，且错误信息里带着出问题的 key。

**顺带清掉的**：`apps/desktop/src/calibration-types.ts` 整个删掉——

**未接的**：`calibration::apply_mark` / `clear_mark` 仍是死代码

真实原因是**这台机器的内存在出错**。跑 `tools\mem-diag.cmd`（只读诊断，见下）

**别再把"重启 WorkBuddy / 停掉其它 session"当解法**——重启只是让症状暂时消失。

**诊断脚本**：`tools\mem-diag.cmd`（双击即可，只读、不改任何系统设置，
报告落在 `tools\mem-diag-<时间戳>.txt`）。它顺带查出本机是

## T15 点击坐标要加「区域内随机」

**操作者 2026-09-19 明确要求记下来**（原话）：

> 鼠标移动的到的坐标，确定好后，再在一定的范围内随机（与区域大小有关）。

### 现状

现在所有点击落点都是**区域的几何中心**（或配置好的固定比例），逐次运行完全一致：

| 动作 | 落点 | 代码位置 |
|---|---|---|
| 点搜索框 | `main_search` 中心 | `runner/search.rs::search_contact_by_keyword` |
| 点下拉里那一行 | 该文字框中心（相对 `search_dropdown` 换算） | `runner/search.rs::click_dropdown_row` |
| 点资料页「发消息」 | 该文字框中心（相对 `contact_profile` 换算） | `runner/search.rs::open_chat_from_profile` |
| 点消息输入框 | `composer` 中心 | `runner/message.rs::prepare_message` |
| 点导航图标 | 命中框中心 | `runner/navigate.rs::navigate_to_view` |
| 点联系人（列表式） | 该文字框中心 | `runner/list.rs::open_chat_from_list` |
| 滚动落点 | `scroll_anchor` / `profile_scroll_anchor` | 同上 |

### 要做什么

落点 = 中心 + **随机偏移**，偏移幅度与**所在区域（或命中框）的尺寸**挂钩，
而不是写死几个像素：

- 幅度必须是**区域尺寸的一个比例**（例如 ±15% 的半宽/半高），
  这样窗口大小、分辨率、DPI 一变，偏移量跟着走。
- 偏移后必须**仍在区域/命中框内**——越界就退到中心。
  否则"随机"会把点偏从"看起来一样的成功"变成"偶发的点空"，
  那比固定中心更难查。
- 随机源要有**可控的种子**（测试里要能固定），不能直接 `rand::random()`：
  否则端到端用例会变成概率性的。
- 幅度**可配**（`0` = 关掉，退回现在的固定中心），默认值要小到"看不出区别、
  但确实不是同一个像素"。

### 为什么这件事值得做（记下来免得将来被当成"没必要"）

固定中心在**同一个控件上重复点击**时是完全可以预测的：长时间反复跑，
鼠标永远落在同一个像素上。随机化的目的是让落点分布像人，而不是像程序。

### 验收

1. 幅度配成 `0` 时，落点与现在**逐字节一致**（回归可控）；
2. 幅度配成非 0 时，连续两次运行的落点不同，但**都落在目标区域内**；
3. 端到端用例用固定种子跑两遍结果一致。

### 发送动作改成「逐字输入 + 点发送按钮」（2026-09-22）

操作者看着上面那条替身任务定下的：**要逐字输入，然后点击发送按钮进行发送**。
替换掉原先的「粘贴正文 + 按回车」。

为什么（两条都是"少一个变量"）：

- **不粘贴**：粘贴要过剪贴板，会覆盖操作者自己的剪贴板内容；它在客户端那边还是
  "一次到达"的，中间没有任何可核对的痕迹。逐字输入与搜索框共用 `type_text` 一条路，
  就不存在"某条输入路径从没被验证过"。
- **不按快捷键**：客户端的发送键因人而异（Enter / ⌘+Enter / 自定义），按错键的表现是
  "输入框里多了一个换行、消息没出去"——看起来像发送失败。点按钮不依赖任何键盘设置。

落地清单：

1. **端口**：删掉 `DesktopPlatform::send_message_shortcut`（连同 macOS 的 `send_enter()`、
   Windows 的 `VK_RETURN` 那条）。新做法不需要它，留着就是一条没人走的路。
2. **`runner/message.rs`** 按阶段拆成 `prepare_message`（聚焦 + 记发送前基线 + 填正文）/
   `type_into_composer`（逐字输入，两条路共用）/ `send_and_verify`（claim 台账 → `Sending`
   → 输入 → 点按钮 → 核验）/ `click_send_button` / `verify_delivery`。
   `click_send_button` 在「发送按钮区」里按 `send_button_text`（默认「发送」）认字，
   点**命中框中心**而不是区域中心：输入框高度随内容变化（一行 → 多行），按钮会跟着上下移。
   命中取**最下面**那一块、同高再取最右——区域画大了会把聊天正文圈进来，
   历史消息里同样可能出现「发送」这两个字。
3. **标定**：`send_button` 变成运行必需项，判据是 `stop_before_send`**而不是工作流**
   （发送那段代码两条路共用）：勾了「只填不发」不要求，「只做导航」也不要求。
   判据在 `runtime/requirements.rs::required_marks` 一处，装配期与界面共用。
   ⚠️ 它**没有出厂默认值**——区域在哪儿只有对着真实窗口框一次才知道。
4. **界面**：`TypingTextSection.tsx` 加「发送按钮上的文字」（`send_button_text`），
   装配期做非空校验：空串在「包含」判断里匹配一切，随手点下去就是最难查的那种"点错地方"。
5. **替身**：`MockDesktop::script_send_button` 声明按钮矩形，`guarded_click` 改成按
   "落点在不在按钮区内"记账（`faults.send` 也只对那一次点击生效）。
   ★ 画面版本号 `+1` 的条件是 `落点在按钮内 || clicks_change_screen`——点中发送按钮
   带来的画面变化是发送本身的因果，不该被"点击没生效"这个模拟否掉。
6. **用例**：`mvp_flow.rs` 的脚本从 4 段变 5 段（发送按钮插在"发送前正文"与"发送后正文"之间，
   自写脚本的 9 处各自补一段）；`runtime/tests.rs` 的 `base_config()` 基线补上 `send_button`，
   并新增 `the_send_button_mark_is_required_only_when_the_task_will_really_send`。

⚠️ **实机验收仍缺**：`send_button` 这块区域、以及按钮上到底是不是「发送」两个字，
**都没在真实客户端上核对过**。真机上第一次跑先开「只填不发」把定位链路验一遍。

## T18 有一条实机用例对环境敏感，会偶发失败

**现象**（2026-09-19 实测）：`cargo test --workspace` 跑到
`crates/platform-windows/tests/windows_contract.rs` 的
`preview_does_not_steal_the_foreground_window` 偶发失败，
报「preview 改变了前台窗口：标定预览绝不能抢焦点」。**单独重跑就过**。

**为什么**：这条用例读一次 `foreground_window()`、调一次 `preview()`、再读一次，
断言两次相同。它跑在**真实桌面**上，只要这期间有别的窗口抢到前台
（操作者点了别的地方、某个后台程序弹了窗），断言就会失败。
它**不是**在测 `preview` 有没有 bug，而是在测「这一秒桌面没被别人动过」。

**怎么处置**（尚未动手，等操作者定）：

- 最省事：在用例文档里写明「跑之前别动鼠标」，失败时先单独重跑确认。
- 稳一点：允许有限次重试（比如前后各读两次取稳定值），或在断言失败时
  先确认当前前台窗口是不是 `Progman`，是的话报「跳过」而不是失败。
- **不要**删掉这条用例：它拦的是「有人为了截图好看往 `preview` 里加一次置前」，
  那是真的会让标定功能时灵时不灵。

⚠️ 这一条**不是**本项目的硬件内存问题引起的，别往那上面查。

### 同类：`ipc_flow` 有一条判据竞态（2026-09-19 已修，别再改回去）

> ⚠️ **2026-09-22 追加：这条竞态连同"人工确认"整条路一起没了**——`awaiting_confirmation`
> 字段、`AwaitingHumanConfirmation` 状态、`confirmation.rs` 与 `task://confirmation-requested`
> 事件都已删除（见 T16 的「移除人工确认」）。本节**保留原文**，因为下面那条
> **通用教训仍然成立**（`wait_until` 的判据必须包含后面要断言的每一个字段）。
> 只是现在没有一个 `awaiting_confirmation` 可以拿来举例了。

**现象**：`a_dry_run_task_travels_the_full_happy_path_through_ipc` 在
`ipc_flow.rs` 里断言 `pending.awaiting_confirmation` 偶发失败。
**同样只在整轮并行（`-j 2`、所有目标同时跑）时撞得上，单独重跑三次全过。**

**根因**（实测，不是猜）：编排层进人工确认是**两步**——

```rust
self.advance(TaskState::AwaitingHumanConfirmation, None)?;   // ① 推进状态（这一步就推视图）
self.runner.ports.confirmation.confirm_send(...)?;            // ② 登记确认请求
```

①里 `state_changed` 算的是 `confirmation.is_pending(id)`，那时请求还没登记 ⇒
推出去的视图是「状态已到等待确认、但 `awaiting_confirmation` 还是 false」。
用例原来只等**状态**，`wait_until` 可能正好取到这两步之间的快照。
窗口只有微秒级，所以只在负载高时踩到。

★ **界面不受影响**：它靠 `task://confirmation-requested` 弹确认框，而那个事件是在
`slots.insert()` **之后**才发的（`confirmation.rs`）⇒ 界面拿到确认框时
`is_pending` 必然已经是 true。**所以别去改编排层那两步的顺序**，
那是为了「先让状态可见、再等操作者」的正常写法。

**修法**：让等待条件就是它要断言的东西——
`|view| view.state == AwaitingHumanConfirmation && view.awaiting_confirmation`。
理由已写在该用例上方。

★ **通用教训**：`wait_until` 的判据**必须包含后面要断言的每一个字段**。
只等其中一个字段，剩下的就变成了「赌这两个字段是同时置位的」——
而它们未必是。同类写法再出现时，症状都是「单独跑必过、整轮跑偶发」。

**背景**：2026-09-19 为「搜索下拉框一截图就收起」加了两种触发方式

**已经测到的**：

- `cargo test -p desktop --features custom-protocol --test ipc_flow hotkey`（3 个用例）：

**没测到的**（只能在真机上看）：

1. **按下去到底会不会触发**。用例能验注册成功，验不了「系统真的投递了 `WM_HOTKEY`」。
   两条真机用例，**都会真的占一个全系统热键**：
   - `cargo test -p platform-windows -- --ignored hotkey`
     ——注册 → 注销 → **再注册同一个组合**，第二次成功才证明注销真的生效了。
     （只测「注册成功」是不够的：注册完什么都不做也算成功，而那正是会留下占坑热键的写法。）
   - `cargo test -p desktop --features custom-protocol -- --ignored a_hotkey_survives`
     ——完整走一遍 `invoke` → 注册 → 注销，顺带验界面显示的那个写法对不对
     （`f12` 要规范化成 `Ctrl+Alt+Shift+F12`）。
2. **热键被别的程序占用时的提示**。拿一个确定被占用的组合注册一次，看界面是不是显示
   「已经被别的程序占用了……换一个再试」。
3. **切页签是否真的自动停用**。进标定页 → 启用热键 → 切到「任务」页 → 回标定页，
   看「已生效」是不是没了；停用之后按那个组合**不应**再有反应。

**已知的取舍**（不是缺陷，别再「修」）：

- 延时秒数（8 秒）**刻意写死**，理由写在 `CaptureTrigger.tsx` 顶部：它是纯界面行为、
  不属于任务配置；做成可配要新增一个配置字段并额外解决跨页签的状态丢失，代价大于收益。
- 热键**只服务标定**：不参与任务执行、不产生任何输入、程序启动时不占用（进标定页才注册）。
- 热键命中时后端**只发事件、不自己截图**——截哪张图取决于界面正在标定哪个界面和配置草稿。

**怎么处置**：上面三条任一条不对，先看 `capture_hotkey.rs` 有没有把事件发出去，
再看 `platform-windows/src/hotkey.rs` 的注册是否成功——界面上的「已生效：Ctrl+Alt+S」
就是注册成功的凭据，它不在就是注册失败，原因会显示在旁边。
**不要**先去怀疑焦点或前台锁定那一套：热键全程不碰焦点。

## T21 运行环境是远程桌面（RDP）：截图这条路会随会话状态断掉

**怎么发现的**：2026-09-19 真机跑导航工作流时 `qwinsta` 显示
`>rdp-tcp#0  llmse  2  Active`，而 `console`（会话 1）是 `Conn` 且**没有用户登录**——
即微信与程序都在**会话 2（RDP）**里。屏幕 2496x1320、缩放 1。

**为什么这是个问题**：

- **输入不受影响**：`SendInput` / `SetCursorPos` 作用于**本会话**的输入队列，
  RDP 会话里照样生效（两条真机导航用例都点成功了，这是直接证据）。
- **截图会受影响**：`capture_region` 从**屏幕 DC** 用 `BitBlt` 抓绝对坐标那块像素。
  RDP 的桌面由客户端渲染，**客户端窗口最小化**或**断开连接**时系统会停止渲染该会话的桌面
  ⇒ 抓到的会是黑屏或上一帧陈旧画面 ⇒ 模板匹配必然失败，或者匹配到错误的位置。
  ⚠️ 组合症状最容易被误判：**输入照常生效、画面却不动**。
  出现「点了没反应」先分清是**输入没到**还是**画面没刷新**，别直接怀疑点击。
- **会话隔离**：程序只能看到**同一会话**里的窗口。若哪天在物理机上登录同一用户并开微信，
  那台微信在会话 1，而程序在会话 2 里——找不到它，且报的是"没有找到可见的顶层窗口"。
- **分辨率 / DPI 会变**：RDP 客户端窗口的大小、本机物理显示器都会改变 2496x1320 这个值
  ⇒ 窗口尺寸一变，四个标定区域都要重标（`contact_panel` 余量只有 ±5px）。

**未做**：

1. **没有"画面能不能渲染"的前置检查**。会话断开时跑任务，现在的表现是
   「找不到图标 / 匹配不到」，**操作者看不出根因是会话断了**。
   可以在真实模式开始前加一次探针（抓一帧看是不是全黑，或读会话连接状态），给明确提示。
2. **没有实测断开后的截图行为**。上面「抓到黑屏」是按 RDP 的已知行为推的，**没验过**。
   验法：断开 RDP 后跑
   `cargo run -q -p platform-windows --example screen_probe -- capture Qt51514QWindowIcon`
   看落盘的那张图是不是全黑。
3. ~~**剪贴板重定向没在 RDP 下实测过**~~ ✅ **2026-09-22 起不再是这条路的变量**。
   发送动作改成「逐字输入正文 + 点发送按钮」之后，任务路径**完全不经过剪贴板**
   （`DesktopPlatform::paste_text` 现在只剩 `screen_probe` 诊断在用），
   所以 RDP 的剪贴板同步延迟影响不到真实任务。`clipboard_read_timeout`
   与 `clear_clipboard_after_paste` 仍留着给诊断那条路。

## T22 光标会被「复位」，而轨迹的可见性还没被验收

**需求原话**（2026-09-19）：「我需要你移动鼠标，我看鼠标没有移动，而且移动要像人一样慢，
不要直接跳过去，应该是有轨迹画过去。」

### 已经做完的

`winapi::move_cursor(x, y, speed_px_per_sec)` 不再一步跳过去，改成沿轨迹走：

- 总时长 = `距离 ÷ 速度`，被 `POINTER_MIN_DURATION`(120ms) 与
  `POINTER_MAX_DURATION`(800ms) 夹住；速度是配置（`pointer_speed_px_per_sec`，默认 1200）；
- 按 `POINTER_STEP_INTERVAL`(8ms，USB 鼠标默认回报率 125Hz) 切步；
- 缓动用 **smoothstep `3t²-2t³`**（起步慢、中间快、收尾慢），**不做随机抖动**——
  抖动会让「同一个点击为什么这次成那次不成」变成查不清的问题；
- 逐步走 `SendInput`(`MOUSEEVENTF_MOVE|ABSOLUTE|VIRTUALDESK`)，不用 `SetCursorPos`；
- `guarded_click` 补上 `ensure_cursor_over_target`（滚动那条路一直有，点击这条路原先漏了）。

**实测**：落点偏差一律 `dx=0 dy=0`；耗时与算出来的一致（980px @ 3000px/s ≈ 327ms）。

### ✅ 「光标会被复位」已排除：是用户自己动的鼠标

一度观察到这个现象：

```
第 1 次：光标 (245,664) → (1106,1133)
（等 3 秒）
第 2 次：光标 (1987,901) → ...        ← 回到 (1987,901)
```

**2026-09-19 已判定是 ①**：两条真机导航用例跑完（点击落在屏幕 (249,603)）之后，
再读光标起点是 **(249,603)** —— **原封不动**，没有被任何东西复位。

⇒ **光标停在程序放的地方**，RDP 不会回写。当时那个 (1987,901) 落在 WorkBuddy
窗口里，正是操作者鼠标所在处。

## T23 「本次走哪条路」改成了运行参数（2026-09-19），还剩「模式」是同款陷阱

**需求原话**（2026-09-19）：

> 「我选择了三条工作流，点击任务运行，执行逻辑全部是进行搜索框，输入文字这个流程。」
> 「我希望是用当前界面选的哪个工作流，就执行哪个，**这个不要保存**。」

### 根因（有实证，不是推测）

界面上的工作流下拉改的是**配置草稿** `draft`；而 `start_task` 读的是**已保存的**
`state.config`。两者不一致时，界面上看起来选了、实际跑的是旧的。
实证：6 条 `data/task-*.log`（19:41）**每一条**都记
「工作流 : 搜索式查找联系人（SearchContact）」，终态全部 `NeedsHumanReview`。
界面上本来有一行警告说"还没保存"，**没拦住**——因为"选工作流"和"保存配置"
在人的心智里是两件事。

### 已做完的

工作流 / 导航目标改成**运行参数** `RunChoice { workflow, nav_target }`：

- `StartTaskRequest.run_choice` **必填**，**没有 `#[serde(default)]`** —— 缺了直接
  反序列化失败，而不是悄悄退回配置里的默认值（"悄悄退回"正是这个 bug 本身）。
- `start_task` 把它交给 `build_runner(config, choice, task, …)`；**既不读也不写**
  `config.workflow`。`RuntimeConfig.workflow` / `.nav_target` 保留，但降级为
  **界面初始值**，装配期不再读。
- 界面：`App` 持有 `runChoice`（**不进 `draft`、不置 `dirty`**），`handleStart` 补进请求；
  `RunChoiceFields` 的三个选择器（模式 / 工作流 / 导航目标）绑它；`TaskForm` **不碰**这件事（用 `TaskFormValues = Omit<StartTaskRequest, "run_choice">` 钉住）。
  ⚠️ `runChoice` 的初值只在**第一次**读到配置时定 —— 写成 `useEffect(…, [info])`
  会让每次「保存配置」都把用户当下选的那条路重置回去。
- 回归用例两条：`runtime::tests::the_run_choice_decides_the_workflow_not_the_config`（装配层）、
  `ipc_flow.rs::start_task_follows_the_request_not_the_saved_config`（完整 IPC 链路）。

### ⏳ 还没做完 / 待确认

1. **真机复核**：跑一条真实任务，确认 `data/task-*.log` 里那行「工作流」与界面上选的一致。
   自动化用例只能证明"请求里的值被读到了"，证明不了"界面把值填进了请求"。
2. ~~**「模式」（演练 / 真实）还是老样子**~~ → **2026-09-19 已改成运行参数**

3. **真机复核（模式）**：界面上切到「真实模式」**不点保存**直接开始任务，

   自动化用例只能证明"请求里的值被读到了"。
4. `RuntimeConfig.workflow` / `.nav_target` / `.mode` 现在只剩"界面初始值"这一个用途。
   等真机复核通过、用户也不再需要"上次用的那条路"作为默认时，可以考虑把这几个
   字段彻底删掉（`config.json` 里的旧值会被 serde 忽略，不会报错）。

### 模式那一条是怎么改的（2026-09-19 同轮）

`RunChoice` 加了 `mode: RuntimeMode`（**放在 `workflow` 之前**）。

★ **它不是"换一组端口"那么简单**，这是它当初被刻意留下的原因。模式决定四件事，
**全部在装配期落地**：

| 判断 | 在哪 |
|---|---|
| 用替身端口还是真实端口 | `build_runner` 里 `match config.mode` |
| 真实模式没有标定尺寸就拒绝开跑 | `build_runner` 开头 |
| 核心层审计记 `dry-run` 还是当前系统 | `RuntimeMode::platform_label()` |
| 要不要把标定窗口交给核心层 | `RuntimeMode::calibrated_window()` |

**做法：不在装配函数里逐条 `if`，而是在 `build_runner` 的**第一件事**就把模式并进
配置副本**：

```rust
let mut config = config.clone();
config.mode = choice.mode;
```

⇒ 上面四处照旧读 `config.mode`，**判据仍然只有一处**，以后再加第五处也不会漏。
后两个方法（`platform_label` / `calibrated_window`）由 `to_runner_config()`
（配置默认值路径）与本次覆盖路径**共用**，避免两处 `match` 漂移。

**界面侧**：

- 模式下拉绑 `runChoice.mode`（**不进 `draft`、不置 `dirty`**），与工作流同款。
- 页头那个模式徽标、`canSave` 的区域校验、演练场景选择器的显隐，
  一律改看 `App` 算出来的 **`activeMode`**（`runChoice.mode ?? info.config.mode`）。
  ⚠️ 不能再用 `draft.mode`——那只是配置里的默认值。
- `RuntimeInfo.notice`（单句）→ **`mode_notices`（演练 / 真实各一句）**。
  模式是运行参数，只发一句就必须在"界面选的"和"配置存的"里选一个，
  而选错的方向恰好是最危险的那个（提示说"演练"、实际在动真窗口）。
  文案仍只有一处：`runtime::RuntimeMode::notice()`。
- **保存配置时会顺手把当前选的模式记成下次的默认值**（`handleSaveConfig` 里
  `{ ...draft, mode: activeMode }`）。否则配置里那个字段永远停在第一次写下的值，
  "上次用的模式"就再也不会被记住。

**回归用例两条**（与工作流那对同款）：
`runtime::tests::the_run_choice_decides_the_mode_not_the_config`（装配层，**两个方向都钉**）、
`ipc_flow.rs::start_task_takes_the_mode_from_the_request_not_the_saved_config`（完整 IPC 链路）。

## T24 「轨迹自检」页签（2026-09-19）：等一次人眼验收

**需求原话**（2026-09-19）：

> 「界面上增加一个页签，增加一个额外的测试功能，我点击按钮，就帮我以点击点为中心
> 　用鼠标移动一个圆形的轨迹，半径为窗口的1/2左右。」

半径口径经确认取 **本程序窗口的 1/2**（不依赖微信是否开着、不依赖窗口标定做没做）。

### 做成了什么

- 平台层：`winapi::circle_points`（**纯计算**，可测）+ `winapi::move_cursor_circle`。
  时长 = 周长 ÷ 速度，夹在 `CIRCLE_MIN_DURATION`(400ms) / `CIRCLE_MAX_DURATION`(8s)；
  步数下限 `CIRCLE_MIN_STEPS`(24)。**匀速、不做缓动** —— smoothstep 是给"从 A 到 B"
  这种有始有终的动作用的，圆周逐段缓动会一顿一顿。开始前先按普通轨迹**走到**圆的起点
  （正右方），不跳过去。
- 命令层：`draw_cursor_circle` → `CircleTraceView`。半径 = `inner_size()` **短边**的一半
  （按宽度算的话，宽扁窗口的圆会超出屏幕高度）。
- 界面：「轨迹自检」页签 → `CursorMotionPanel.tsx`。**点按钮 → 倒计时 3 秒 → 再调命令**，
  操作者可以在倒计时里把鼠标挪到想当圆心的位置。
- 命令层**单独成模块** `src-tauri/src/cursor_trace.rs`（不是塞进 `lib.rs`）：
  `lib.rs` 的基线是 1903 行，这段自己就有近百行，塞进去就破了。
  注册点仍然只有 `lib.rs` 的 `with_commands` 一处。搬移的坑记在 `CONVENTIONS.md` §9。
- 倒计时的"怎么数"抽成了 `src/countdown.ts`（`useCountdown` / `COUNTDOWN_TICK_MS` /
  `remainingSeconds`），`CaptureTrigger` 一并改用它。**秒数不共用**（那边 8 秒要够切回
  客户端输完联系人名，这边 3 秒只是挪一下手）。
  ⚠️ `WindowPicker` **刻意不改**：它那个定时器每跳一次还要顺便采一次"光标下是哪个窗口"，
  数与采是同一拍，拆开会出现"倒计时结束了但最后一次采样还没回来"。

### 取舍与已知限制

1. **速度不收界面参数**：光标速度目前不是可配项（`to_runner_config()` 给平台层用的是
   `..default()`，速度就落在 `WindowsDesktopConfig::default().pointer_speed_px_per_sec`）。
   所以命令**只认那一个来源**，并把实际用的值回报给界面。
   让界面传值 = 在 TS 里再抄一份默认值 = 两处真相：以后有人调了平台层默认值，
   自检里看到的快慢会和任务里不一致，而**两边都看不出来**。
   将来如果速度变成可配项，这条命令要改成**从配置读**，而不是从请求参数读。
2. **不受运行模式限制**（演练模式下也能用）：它只移动光标，不点击、不输入、不抢前台。
   与「界面标定」那组命令同一个理由。
3. **一圈走完才返回**，界面在期间没有任何中间反馈（只有按钮变灰）。
   这是刻意的——光标自己就是那个反馈；做成流式回报要新开一条事件通道，
   为一条演示功能不值得。**倒计时存在的第二个理由就是它**。
4. 切页签会卸载面板，倒计时与上次的结果都会丢。与其它页签一致（一次性展示，不必留住）。

### ⏳ 还没做完

1. **人眼验收**：还没人真的点过那个按钮。要看的就三件事 ——
   ① 光标是**走**过去的（不是跳过去）；② 走出来的确实是个圆（不是椭圆、不是多边形）；
   ③ 快慢是否合适（`CIRCLE_MAX_DURATION` 触顶时实际速度会快于配置速度，这是刻意的取舍）。
   → 这条同时是 **T22** 那个"轨迹可见性还没被验收"的验收手段。
2. ✅ **`winapi.rs` 已经拆到基线以下**（2026-09-19，两刀）：1215 → 985 → **796**
   （基线 862）。光标轨迹 → `winapi/cursor.rs`(267)，输入原语 → `winapi/input.rs`(228)。
   同一天里 `runtime.rs`(1049→984)、`lib.rs`(1922→1900)、`RuntimePanel.tsx`(858→288)
   与 `IconLibraryPanel.tsx`(1064→808) 也各拆了刀。详见 T17。
3. `ipc_flow.rs::a_circle_trace_comes_back_self_consistent` **默认 `#[ignore]`** ——
   它会真的画一圈、抢走鼠标。要跑：
   `cargo test -p desktop --features custom-protocol -- --ignored a_circle_trace`
   圆周算得对不对另有 7 条**不碰光标**的纯计算用例每次都会跑
   （`platform-windows/src/winapi/tests.rs`）。

### 2026-09-20 追加：画完**不回起点**，并回报**实测**终点

**需求原话**：

> 「鼠标滑圆，我好像只看到鼠标的样式变了，没看到鼠标动。你画完以后不要移回原来的
> 　位置，这样我就知道它有没有真的移动。」

闭合的一圈，终点必然落回起点，于是"走过一整圈"和"它根本没动"在**事后看光标位置**时
是分不出来的（半径不大时尤其分不出来）。两处改动：

1. **终点离开起点**：走满一圈后**再多走 1/4 圈**（`CIRCLE_EXTRA_TURNS`），
   停在圆上的另一个位置，与起点差 90°。点的间距仍按弧长均匀，所以轨迹照样匀速。
   `circle_points` 多了一个 `turns` 参数（`1.0` = 闭合的一圈，语义没变），
   那几条纯计算用例只加了个实参，**断言一条没动**。
2. **回报实测终点**：`CircleTrace` 增加 `end` —— 走完之后**重新读一次**光标位置
   （不是把算出来的终点当结果）。界面显示「实测终点 (x, y) · 离圆心 N 像素」，
   走对了 N ≈ 半径；**N 接近 0 就说明整段轨迹没生效**，而那正是
   "按钮正常返回、屏幕上什么都没发生"的那种情况——光看返回值发现不了。

★ 刻意**没有**在代码里判"算不算动过"：那需要一个容差阈值，而阈值定在哪里都是拍脑袋；
这是给人看的自检，**没有任何自动判据依赖它**。数字并排给出来，由人一眼对比。

⚠️ 上面这条改动**不解决**"光标到底为什么看起来没动"。如果实测终点与圆心重合，
那说明 `SendInput` 的绝对坐标没生效（坐标被夹 / 被前台锁定吞掉），
下一步该查 `winapi::cursor::move_cursor_absolute` 的虚拟桌面归一化，
以及用 `screen_probe move <前缀> <x> <y> [速度]` 单独量一次（那是"到底动没动"的
既有判据）。**别再靠肉眼猜。**

## T25 「窗口一闪就退出」：加启动期落文件日志 + `run.cmd` 不再一闪而过（2026-09-19）

**需求原话**（2026-09-19）：

> 「运行 run.cmd 进程启动后，我看到窗口闪现了一下又退出了」

### 先说要紧的：**没复现出来**

所有自动化启动方式（后台 `&`、`Start-Process`、`cmd /c run.cmd`）进程**都活着**。
所以这一轮**没有去猜原因**，而是把它做成**可诊断的**——下次再出现，现场要留得下来。

### 为什么原来什么都看不到

GUI 程序没有控制台；而"窗口还没出现就退出"这类故障（数据目录建不出来、
应用状态初始化失败、WebView2 起不来）**全发生在窗口出现之前**。
`run.cmd` 自己也是启动完就结束 —— 两件事叠在一起，操作者看到的就只有「窗口闪了一下」，
**没有任何文字可看**。

### 做了两件事

**① `src-tauri/src/startup_log.rs`（新模块，165 行）→ `data/startup.log`**

- `begin()` 在 `run()` 的**第一行**调用，记：启动横幅、工作目录、数据目录、可执行文件路径。
  之后 `setup` 成功 / 失败各记一条。每行带 `+123ms` 相对偏移（省掉日期格式化依赖）。
- ★ **第一条写下去时截断**旧文件，之后追加 —— 这份日志只描述**这一次**启动。
- ★ **写失败一律静默**：观测手段不该成为新的失败点。
- ★ **数据目录建不出来时退回工作目录记** —— 否则最需要它的那种故障反而没有日志。
- ★ 另装了一个 panic 钩子，**包一层原有钩子、不替换**（替换会把原有的 panic 输出弄丢）。

**② `run.cmd`：启动后等 4 秒再确认进程还在**

`start` 之后 `ping -n 5 127.0.0.1`（⚠️ **不能用 `timeout`**：标准输入被重定向时它直接报错），
再 `tasklist /FI "IMAGENAME eq desktop.exe" | find /I "desktop.exe"` 判断存活。
不存活 ⇒ `type` 出 `startup.log` 全文 + `pause`，把"窗口闪一下"变成一屏能读的文字。

### ⏳ 还没做完

1. **等一次真实复现**：用户再遇到时，把 `run.cmd` 窗口的输出（或 `data/startup.log`）发回来。
2. ⚠️ 判读要点：**连 `startup.log` 都没有** ⇒ 程序根本没跑到 `run()` ——
   那不是本程序自己的问题（缺 DLL、被安全软件拦下、双击的不是这个 exe）。
   这条已经写进 `run.cmd` 的提示文字里。
3. 已知不完美：若用户**本来就有**一个 `desktop.exe` 开着，`tasklist` 那条会误判成"启动成功"。
   代价可接受（那只可能是用户自己先跑的），但要写在这里。

## T26 「要点哪一个图标」改成从**图标库目录**里选（2026-09-20）

**需求原话**（2026-09-20）：

> 「图标选择，应该使用图标列表进行选择，这样才能关联上一致。」
> 「目录那一级，目录下的多个图标循环匹配，`data/icons` 的子目录」

### 原来错在哪

`NavTarget` 是一个**只有两个变体**的枚举（`Contact` / `History`），下拉里显示的是
两个抽象名字「联系人图标」「聊天历史图标」；而图标库里实际存的是
**发现 / 收藏夹 / 聊天历史 / 通讯录** 四个目录。

于是两件事对不上：

- 想测「收藏夹」—— **下拉里根本没有它**；
- 「联系人图标」背后到底是哪个目录，只能靠"我在图标库页勾了哪个"去反推，
  而那两组勾选框里各勾了几个名字，下拉上是看不出来的。

### 改成了什么

`NavTarget` 枚举**删掉**，`RunChoice::nav_target` / `RuntimeConfig::nav_target`
改成 **`String`（图标库里的目录名）**：

- 下拉直接列出 `data/icons/` 的**一级目录**（就是「图标库」页列表里那几行），
  每项后面标着它有几张图。选中一个 ⇒ **那个目录下的全部图一起参与匹配、取最高分**
  —— 它们本来就是同一个图标的选中 / 未选中 / 带气泡等状态，不该被当成不同图标比高低。
- 核心层不再问"哪一组模板"：`RunnerConfig` 的 `nav_target: NavTarget` 与
  `history_icon_templates` 一起删掉，换成 **`nav_target_label: String`**
  （只进日志与失败信息）。**装配期**把两种来源收敛成同一件事——
  「只做导航」用请求里选的那个目录名；查找前切视图用配置里那组"联系人视图"图标
  —— 两者最后都落到同一个 `nav_icon_templates`。
- 「用于聊天历史导航」那个勾选框**删掉**：它当初存在的唯一理由就是给
  `NavTarget::History` 喂模板，枚举没了它就是死配置。「用于联系人导航」保留
  （查找式任务"开始前先切到联系人视图"仍然靠它）。
- 空名字 / 名字在图标库里不存在 ⇒ **装配期直接拒绝**，不兜底挑一个
  （兜底挑错的表现是"点到了别的地方"，而任务照常跑完，看不出任何异常）。
- `RunChoice` **不再实现 `Copy`**（里面现在有 `String`），`build_runner` 改成收 `&RunChoice`。

### 回归用例

- `runtime::tests::navigate_only_loads_every_variant_of_the_chosen_icon`（装配层）：
  目录下的变体全载入、名字不存在要拒、没选也要拒。
- `ipc_flow.rs::start_task_navigate_only_takes_the_icon_name_from_the_request`（完整 IPC）：
  钉住**请求里的字段名** —— 只在装配层测的话，字段名写错照样全绿，
  而线上表现是"选了一个图标、跑起来却是另一个"。

## T27 「只做导航」点开始什么都不发生（2026-09-20 实测）

### 现象

选了工作流「只做导航」、在「要点哪一个图标」里选了「通讯录」、点「开始任务」，
**界面上没有任何反应**：任务列表里没有新条目，`data/` 下连 `task-*.log` 都没生成。
看起来像"后端判断逻辑坏了"。

### 根因：**必填项没有按工作流区分**（前后端各一份，且都是无条件的）

- 命令层 `start_task` 一上来就 `if contact.is_empty() → Err` / `if text.is_empty() → Err`，
  **不管这次跑的是哪条路**。而「只做导航」既不找人、也发不出消息，那两个字段对它
  根本没有意义。
- 界面 `TaskForm` 的 `canSubmit` 是 `contact !== "" && text !== ""`，
  于是那两个框空着时「开始任务」是 **`disabled`** ⇒ `onClick` 根本不触发
  ⇒ `error` 一直是 `null` ⇒ **既没反应、也没报错**。
- 按钮文案只区分 `running`（"已有任务正在执行"），不区分 `canSubmit`，
  所以它看上去就是一颗普通的「开始任务」。

### 修法：判据收敛到一处，界面只渲染

- 新增 `runtime::workflow_inputs(workflow) -> WorkflowInputs { contact, message }`
  —— **这条判据只此一处**。`Workflow::NavigateOnly` 两项都是 `false`。
- `workflow_requirements` 每条工作流多下发 `needs_contact` / `needs_message`；
  `start_task` 按 `workflow_inputs` 校验；`TaskForm` 按下发值决定
  **那两个框显不显示**、`canSubmit` 怎么算。
- ★ **`null`（还没问到 / 问不到）时一律放行**，交给命令层拒绝并说清原因：
  **拒绝是看得见的，点不动是看不见的**。
- 「只做导航」时 `TaskForm` 整块输入都不显示（留着一个填了也没用的框，
  下一个人还会去填它），并给一句说明指路到「要点哪一个图标」。
- 日志表头那行 `目标联系人` 对这条路显示「（不适用：只做导航）」，
  界面上那两处显示「（这条工作流不找人）」——空着会被当成"漏填了"。

## T28 导航图标**模板匹配分数不够**（2026-09-20 **已定位**：模板截的是「选中态」，画面里是「未选中态」）

### ★★ 根因（已确证，不是推测）

**导航图标在「选中 / 未选中」两种状态下是两套字形，不只是换个颜色**：

| | 字形 | 颜色 | 背景 |
| --- | --- | --- | --- |
| 未选中（任务运行时看到的） | **描边线稿**（中间是空的） | 灰 `#5A5A5A` 左右 | `#E0E0E0` |
| 选中（模板截到的那一张） | **实心填充** | 绿 `#00C375` | `#E0E0E0` |

两个状态**互相比只有 0.55 左右**，阈值 0.700 ⇒ 永远转人工。

**怎么确证的**（不是看代码推的）：用只读探针 `screen_probe` 对着真机窗口量了一次
（窗口 896x648 @(152,202)），分数与位置**和 6 条任务日志逐位复现**：

```text
screen_probe findicon "casper" "data/icons/通讯录/1.png,data/icons/收藏夹/1.png" 0.7 0 0 0.1 1.0
  data/icons/通讯录/1.png  (40x38)   最高分 0.5511  [不足]  搜索区内 (18, 142)
  data/icons/收藏夹/1.png  (38x35)   最高分 0.5319  [不足]  搜索区内 (19, 144)
```

⇒ 所以**不是陈旧帧**（同一台机器、另一个时间点，分数一模一样），
**也不是"模板没截到图标"**——位置是对的：`(18,142)+38/2 = 161`，
正好是屏幕上「通讯录」图标的中心（实测图标在窗口 y 150–172）。
**位置对、分数低**，正是"字形不一样"的典型表现。

把真机那一列图标放大看，一眼就清楚了：未选中的是**空心描边**的「人形 + 两条横线」，
而 `data/icons/通讯录/1.png` 是**实心绿**的同款；「收藏夹」同理（空心线框立方体 vs 实心绿立方体）。

### 修法（**不用改代码**）

`locate` 本来就是"多张变体取最高分"，而图标库**一个名字下可以存多张图**。
所以只要把**未选中态**也存进去：

1. 先点一下**别的**图标，让目标图标回到**未选中**（灰色描边）状态；
2. 到「图标库」页重新截一张，**名字填一样的**（`通讯录`）⇒ 存成 `通讯录/2.png`；
3. 两种状态各存一张最稳——任务跑的时候目标可能恰好已经被选中。

★ **2026-09-20 已经代截好了**（`通讯录/2.png` 与 `收藏夹/2.png`）：
用只读探针 `template` 从真机截、`findicon` 量，**两张都是 1.0000**，
点击点正好落在各自图标中心。⇒ 现在跑「只做导航」应该能过阈值了（待用户验收）。

★ 代码侧只加了两处**提示**，防止再踩：`IconLibraryPanel` 的说明里写清了
"两套字形、要截未选中"，`candidate_report` 的失败信息里也带了同一句话
（失败那一刻人正好在看那里）。

### 实测数据（`data/task-*.log`，全部 6 条导航记录，都是同一原因）

| 模板 | 尺寸 | 最高分 | 命中位置（图像坐标，相对搜索区） |
| --- | --- | --- | --- |
| `通讯录/1.png` | 40x38 | **0.551** | (18, 142) |
| `收藏夹/1.png` | 38x35 | **0.532** | (19, 144) |

阈值 `nav_icon_min_score` = 0.700；搜索区 = `nav_strip [0,0,0.1,1.0]` → 屏幕 (46,108) 97x734。
任务全部止于 `NavigatingToView -> NeedsHumanReview | AMBIGUOUS_VISION`，
**所以界面上看不到任何动作**（鼠标没动、也没点）。

### 「两个模板命中同一处」怎么解释（当时最可疑的一点）

两个模板的峰值位置差 (1, 2) 正好是尺寸差 (2, 3) 的一半 ⇒ 它们匹配到的是
**同一块内容**，也就是同一个图标（「通讯录」）——而「收藏夹」的模板在它上面
拿到 0.532、在自己真正的图标上拿到更低。这不是"两个都没找到"，而是
**"两张实心模板都更像那个实心/描边的混合结构"**；真正的信号是
**通讯录那张在自己正确的位置上也只有 0.551**，这一条当时就被记下来了。

### 已排除

- **不是**陈旧帧（RDP）：真机复现的分数与日志逐位相同。
- **不是**模板是缩放过的预览图：像素统计显示过渡色只占 5.1% / 6.8%、

### 诊断手段（可复用，已做）

**① 失败时自动报「每个模板的前几名」**（`crates/vision/src/template.rs` 的
`top_candidates` / `candidate_report`）。分数低于阈值时，失败信息里多一段
"各模板前 3 个候选（分数@坐标）"。

**它分辨的是什么**：`0.55` 有两种完全不同的成因，只报最高分时它们在日志里
一模一样 —— ① 有**明显的峰**、只是峰不够高（模板确实是那个图标，但画出来的样子
变了）⇒ 重截模板；② **到处都差不多**（搜索区里根本没有对应物，最高分只是噪声）
⇒ 查搜索区与几何，重截模板没用。**本例就是 ①**。

⚠️ 抑制重叠**必须按分数定强弱、不能按扫描顺序**：扫描是从左上往右下走的，
先扫到的边缘位置（0.42）会先把真正的峰（0.98）当成"同一处"压掉，
结果恰好把要说清的事说反。用例 `the_diagnostic_reports_distinct_peaks_not_neighbouring_pixels` 钉住了这一条。

⚠️ 它是**单线程再扫一遍**，97×734 搜索区配 40×38 模板是**秒级**（debug）。
所以**只**在已经决定转人工之后才调用，绝不能放进主路径。

**② 只读探针直接量真机**（★ 本例靠它定的案，比跑任务快得多）：


填 `0.1` 会被拒成"必须是整数"，于是**量不到配置里真的在用的那个区域**。

### 设计要点

- **判据与轨迹同源**（守 `CONVENTIONS.md` §1.3）。把判定体抽成**纯函数**，
  一次返回「结论 + 轨迹」：
  `Decision { step, question, rule, outcome, candidates: Vec<Verdict> }`、
  `Verdict { text, confidence, bounds, verdict: 通过/淘汰, reason }`。
  工作流只取结论、顺手报轨迹。**绝不允许另写一处判据去生成轨迹**——
  那样两条线迟早不一致，而轨迹恰恰是用来判断判据的。
- 端口：给 `DiagnosticRecorder` 加**带默认空实现**的 `decide()`，
  现有实现者（含测试替身）不用改。
- 事件流：`data/tasks/<id>/events.jsonl`，一步一条（`{"v":1,"kind":"read"|"decision",…}`，
  含区域、帧尺寸/缩放、boxes+置信度、指纹、判定）。**格式只定义在 `apps/desktop`**，
  core 不碰落盘格式；图仍落 `steps/`，事件只引用文件名。
- fixture **就是 `events.jsonl`**，不另立第二套格式；重放支持
  `--min-confidence 0.7` 这类覆盖，阈值调参不必再上真机。
- 查看器默认落在**失败那一步**（而不是 60 步总图）：左图右表，
  每个候选一行带「为什么没被选中」，可搜索、可跳步。

### 设计要点

**（一）raw 原料：把「可重跑的现场」存全（只在本机 `data/tasks/<任务ID>/raw/`）**

- `raw/NN-步骤名.png`：**未标注**的 OCR 输入图（就是 `observation.frame` 的字节）；
  ★ 实测依据：`events.jsonl` 里 `frame` 的 w/h 与 `region` 的 w/h **相等**
  （2026-09-21 那份现场是 360x420 对 360x420）——即"这一帧"就是裁给 OCR 的那块，
  `region` 只记它在屏幕上的位置。
- `raw/NN.json`：外部 OCR 进程 stdout 的**原文**（不是解析后的 `boxes`）
  ——将来换引擎、换平台时能直接 diff，而"那次到底读出了什么"也终于有原始凭证。
- 落盘点仍在 `task_diagnostics`；`read` 事件加两个字段指过去（`ocr_input` / `ocr_raw`），
  **格式仍只定义在 `events.rs`**（T29 的规矩不变）。
- ⚠️ **必须是未标注的**：蓝框压在字上，拿标注图重跑 OCR 会读出另一套结果，
  那份现场就废了。这是"能不能重跑 OCR"的唯一前提。

**（二）期望值：人给一次，仓库永久受益**

- 失败时界面追问一句「这一步本来应该怎样」：从候选里点一个正确项，
  或选「其实这一步不该点任何东西」；落 `expect.json`：

```json
{"step": "搜索下拉识别", "should": {"kind": "click_text", "text": "李小明"},
 "verdict": "should_pass", "note": "标题被 OCR 读成低置信度 0.61，人眼能看到「联系人」"}
```

- ★★ **期望值只能由人写入。** agent 可以改代码、改参数，
  **不许改 `expect.json`**——否则闭环就成了自己出题自己判卷，通过率毫无意义。
- 收编命令：`replay --adopt data/tasks/<任务ID> -o data/cases/<用例名>/`，
  把 `raw/` + `events.jsonl` + `expect.json` 复制成一份**本机**用例，
  并**由生成器守卫**（照 T29：用例是产出的，不是手写的）。
  ⚠️ 落点是 `data/`（已忽略）而**不是** `tools/replay/tests/fixtures/`——
  用例里既有图、也有真实姓名文本。
- ★★ **本地目录即用例**：`data/cases/*/` 一个子目录一条，`replay --all` / 测试**遍历目录**，
  收编新现场只丢文件、**不改代码**——这是"过程能沉淀成用例"的关键。
  仓库里那条假场景用例同样做成"目录即用例"（`tests/fixtures/假场景名/`），
  这样两者用**同一个读目录的实现**，不需要两套加载逻辑。

**（三）归因到层：一条命令回答「卡在哪一层」**

三层各自都能一句话判定，`replay` 直接把结论打出来，人不用自己拼证据：

1. 干净图上人眼能认、`boxes` 里没有或读错 ⇒ **OCR / 预处理层**；
2. `boxes` 里有、候选表里被淘汰 ⇒ **判据层**（T29 已通）；
3. 判据选中了、却没点对 ⇒ **坐标 / 点击层**。

**（四）agent 闭环：三件事必须齐**

1. `replay --json`：结论、**卡在哪一层**、每个候选、与 `expect.json` 的差异。
   今天只有给人读的中文散文报告，agent 去解析它是脆的；
2. **一条命令跑全部现场**：本机 `replay --all data/cases/*`（真实现场，含图，能跑到 OCR 层）
   与 `cargo test -p replay`（仓库里的假场景，只到判据层），都输出 before/after 表
   「N 条由失败变通过、M 条由通过变失败」——**这就是回归门**。
   ⚠️ 两台机器的结果**天然不同**（现场只在那台机器上），所以"全绿"这句话本身要带上下文：
   agent 报数时必须说清是**本机现场**还是**假场景**。
3. **边界**：agent 只能改代码与参数，且必须给出**全量**差异，
   不许"改到某一条通过就收工"。

⇒ 循环长这样：跑全量 → 读 JSON 差异 → 归因到层 → 改代码 → 重跑 → 报数。
判定标准是**人的期望值**，不是它自己的判断。

**（五）加强项（本轮不做，先记在这里）**

- **多倍率扰动重跑**：同一张 raw 图用 `--upscale 1/2/3` 各跑一遍，看结论稳不稳。
  它回答的不是「为什么这么判」，而是「**这个判据靠不靠得住**」；
- **每块文字的裁剪胶卷**：候选框的小图拼一张，一眼看 OCR 把字形认成了什么，比 `0.61` 直观；
- **双引擎交叉**：`winocr` 与 `macosocr` 对同一张图各跑一遍，不一致即是信号（跨平台移植时尤其值）；
- **相邻帧 diff**：失败步与上一步的图对比，回答「界面到底变没变」——「点了没反应」的常见根因。

### 补强（2026-09-21 用户要求）：标注图底图改「整窗 + 区域框」，图标步骤补命中框

用户原话：「每一步的截图，搜索区域都应该标记渲染好保存，这样方便查问题，
参考搜索框搜索下拉的做法。」两件事一起做：

1. **底图改成整窗**（`Observation::window` / `WindowShot`）。只贴裁图时，图上那圈
   橙色的「要识别的区域」恒等于图像边界——**看不出这块区域落在窗口的哪个位置**，
   而"区域标定偏了"（框到头像列、框到标题栏）恰恰是最常见的一类故障。
   代价：每一步多截一次整窗；取不到（还没进客户端 / 演练替身 / 截屏失败）就**退回裁图**，
   诊断永远不该让任务失败。★ 只读 `enter_client` 时定下的窗口矩形，**不**调
   `ensure_calibrated`——那个为了"接下来点的就是它"会抢前台，观测不该有副作用。
2. **图标匹配补命中框**（`Observation::icon` / `IconHit`）。图标上**没有文字**，
   OCR 那套（绿框 + 右侧文字栏）对它不适用，"它把哪个图标认成了目标"是这一步
   唯一的可读结果。命中要等匹配之后才知道，所以同一步**补报一条**（`导航图标命中`），
   复用**刚匹配过的那一帧**、不重截——重截一张会让画上的框与画面对不上。
   图上画成**蓝框**（与文字框的绿框区分），右侧栏列一行「模板名 + 分数」。
3. 顺带把 `vision/src/render.rs` 的用例拆到 `render/tests.rs`：主体加完这两样就过了

## T31 单步超时「超在哪儿」：日志带代码出处 + 分段耗时（2026-09-22 已落地）

### 现象（用户给的原始日志）

```text
[2026-09-22 10:31:13.960] WaitingForClient -> NavigatingToView  | 目标：通讯录图标
[2026-09-22 10:31:38.953] NavigatingToView -> NeedsHumanReview  | 步骤超时：点击导航图标 超过单步上限 20s
```

两件事：① 定位这一步的耗时代码；② **日志打印要带上代码定位信息**（方法名 / 行号之类）。
第 ② 件的动机就是第 ① 件逼出来的——旧日志只有"谁说了什么"，没有"话是从哪儿说的"。

### 定位：`TemplateLocator::locate` 一个人吃掉 ~16s

拿那次任务的盘上材料把 25s 拆开（`data/tasks/<ID>/events.jsonl` 每步的时间戳，
标签就是 `capture_frame` 的 label）：

| 区间 | 耗时 | 里面只有 |
| --- | --- | --- |
| 任务开始 → step1「切换视图前」 | ~0.7s | 解析区域 + 截候选区 |
| step1 → step2「导航图标搜索区」 | **2.46s** | step1 的诊断落盘（渲染+编码+写盘）+ 截导航条 |
| step2 → step3「导航图标命中」 | **18.3s** | 诊断落盘收尾 + **`icons.locate`** |
| step3 → 超时 | **3.5s** | 命中那一步的诊断落盘 + 守卫 + 点击 |

减去每步约 1.2–2s 的诊断开销（由前后两段反推），**`icons.locate` ≈ 15–16s**，是绝对主犯。
（收尾那张总图另花了 6.2s：任务已经结束，不进单步预算，但同样得报出来。）

**为什么这么慢（不是阈值问题）**——开销 = 搜索位置数 × 模板像素数 × 通道数：

1. 搜索区是**整条导航条**，Retina 下按物理像素算（这一次是 198×1234）；
2. **4 张模板，每张都把这片区域逐位置扫一遍**；命中分数已经是 1.000 也不会早退；
3. 跑的是 **debug 构建**。

量级核对（用仓库里的用例，不是估的）：`vision` 的
`template::tests::measure_a_realistic_navigation_strip`（73×734 搜索区 + 26×26 模板，debug）
= **175ms**；按"位置数 × 模板像素数"放大到上面那份工况约 **5s/模板 × 4 ≈ 20s**，
与实测 15–16s 同一量级。
★ 顺带纠正一个容易带偏的猜测：七档金字塔（`TEMPLATE_SCALE_PYRAMID`）**不在主路径上**
（`locate` 走的是单尺度，那几个 `best_match_pyramid*` 目前是 dead code），别照它去算。

### 落地：日志带出处 + 分段耗时

## T32 ✅ 已做（2026-09-22）：搜索式那次点击**未必**落在资料页，补一条跳过分支

### 现象（操作者口述）

搜索式工作流点完搜索下拉里的那一行之后，**通常**落到联系人资料页、要从那儿点「发消息」进聊天；
但对方**已经有会话**时，客户端会**直接打开那份聊天记录**——资料页根本不出现。
旧代码把"资料页上没认到目标"和"点击没生效"当成同一件事报错，于是这种落点必定失败，
而失败文案（"资料页上读到的是……与目标不一致"）看起来像是**点错了人**，指向完全错误的方向。

### 判据顺序：先资料页，只有"没认到"才去问聊天标题

**不能**反过来先看聊天标题区：本机标定里 `chat_header = [0.330, 0.0, 0.670, 0.1]`、
`contact_profile.rect = [0.333, 0.096, 0.660, 0.896]`——**两块只差 2 像素**。
先看标题区会把"还在资料页"误判成"已在聊天里"，接着那次输入就会落到没有输入框的界面上。
所以顺序只能是：**先核验资料页 → 只有它报"没认到" → 才拿聊天页标题定论**，
且定论用的是**同一条**聊天标题判据（`verify_chat_header`），不新开一套。

### 落地

1. **`runner/search.rs`**：新增 `ProfileReview { Verified, NotFound(AutomationError) }`——
   `verify_profile` 不再自己判定成败，只把结论交回调用方；**"点击根本没生效"仍是硬失败**
   （那时画面一个像素都没动，继续往下走等于在可能卡死的界面上打字）。
   新增 `open_chat_from_dropdown`：`Verified` 走原来的「点发消息 → 核验标题」；
   `NotFound` 则直接核验标题——过就算"客户端直接打开了已有会话"，把跳过这件事写进证据；
   也没过就报**资料页那条原因**（它回答的是"那一次点击把界面带到哪儿去了"），
   同时把标题核验的结果一并记进证据。
2. **`runner/mod.rs`**：搜索式把「核验标题」一起交给 `open_chat_from_dropdown`（两种落点收尾相同）；
   列表式保持原样。`mod.rs` 1483 → 1509 → **1507**（净减 2，见 §9「只减不增」）。
   ⚠️ 2026-09-22 搜索式接入发送时又动了同一个文件，现为 **1510**（见 T16 末尾那节）。
   ⚠️ 同一天再把发送动作改成「逐字输入 + 点按钮」后是 **1541**（还超 500 的基线，
   见 §9 与 T17）。
3. **`state.rs`**：补一条边 `VerifyingProfile → VerifyingChatHeader`。
   少这条边，真实场景会在半路报"非法转换"，现象看起来像流程坏了，看不出是"界面本来就长这样"。
4. **用例**：`state/tests.rs::the_search_flow_can_skip_the_profile_entry_when_the_chat_is_already_open`、
   `platform-mock/tests/mvp_flow.rs::a_click_that_lands_in_an_existing_chat_skips_the_profile_page`
   （断言终态 `Completed`、`states` 含 `VerifyingProfile` 但不含 `OpeningChatFromProfile`、点击数/输入数与证据文案）。
   ⚠️ 终态那一条 2026-09-22 随"搜索式接入发送"从 `Prepared` 改成了 `Completed`。

### 补充（2026-09-22 晚）：第二种"没落成"——认到了人、却没有「发消息」入口

**实机现场**：`data/tasks/775ce13e-…`，终态 `NeedsHumanReview`，原因
"资料页里没有找到「发消息」这个入口（已经滚到最下面）"。
看 `raw/13-资料页识别.png`（未标注的那张 OCR 输入图）：**界面已经停在聊天页上**了
——左边是会话列表、中间是聊天记录（"用 11 的 s 版本"、"无所谓"）、
底部输入框和「发送」按钮都在。也就是说上一节那条跳过分支**没被触发**：
`verify_profile` 认到了人。原因有两层：

- 聊天页右上栏顶部显示的也是他的名字（T32 上一节说的"两块区域只差 2 像素"）；
- 更直接的：聊天记录里就有一条 `太过活跃 田志清: 用 11 的 s 版本`，名字原样躺在
  `contact_profile` 区域里，匹配器当然认。

于是硬失败落在 `open_chat_from_profile` 那句 `ok_or_else` 上——**一次本来能走完的
任务被判成失败**，而文案把人引向"标定偏了 / 客户端版本变了"，方向正好相反。

**改法**：把同一个成因的第二种表现也交回调用方。

1. `runner/search.rs` 新增 `ChatEntry { Opened, NotFound(AutomationError) }`，
   与 `ProfileReview` 成对。`open_chat_from_profile` 在资料页里翻不到入口时
   **返回 `NotFound` 而不是报错**（一个像素都不点），把原因带回去。
2. `open_chat_from_dropdown` 把两种 `NotFound` 合成一条路，都去核验聊天标题：
   - 标题对得上 ⇒ 判定"客户端直接打开了已有会话"，把"已跳过那两步"写进证据；
   - 对不上 ⇒ 报**分类那条**原因（这里报"没有入口"），并把标题核验的结果
     一并记进证据（它是"不在资料页"这个判断的另一半依据）。
3. ⚠️ 这条支路**已经**进了 `OpeningChatFromProfile`：状态进了、入口没找到，两者
   不矛盾——"找过入口"就是这一步做的事。所以它的 `states` 里**有**
   `OpeningChatFromProfile`，与上一节那条老支路（不含）不同。**两个用例分别钉住**，
   免得将来有人把两条支路"统一"成一条。
4. **用例**（`platform-mock/tests/mvp_flow.rs`）：
   - `a_profile_without_the_chat_entry_is_skipped`——原用例是
     `a_profile_without_the_chat_entry_is_a_human_review`，**行为反转**：
     终态 `Completed`、点击数 5（少了「发消息」那一下）、证据含"已跳过"；
   - `a_missing_chat_entry_whose_header_also_mismatches_is_a_human_review`——
     两条路都没认下来时**才**转人工，报"没有入口"那条。
5. **顺带确认了一件让人担心的事**：跳过之前，`scroll_profile_to_bottom` 已经滚过
   这块区域了。滚轮方向按"向下 = 看更靠后的内容"定，在聊天页里就是**朝向最新的
   那条消息**——所以它要么什么都不做（本来就在最底下），要么把聊天滚回最底下，
   **不会**滚进历史记录。这条写进了 `scroll_profile_to_bottom` 的文档：
   否则"在聊天页上滚了资料面板"看起来像会把视图搞乱，跳过分支就不敢走了。
