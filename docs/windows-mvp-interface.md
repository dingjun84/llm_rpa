# Windows MVP：平台与视觉接口契约

本文定义实现阶段的 Rust 端口。业务流程只能依赖这些端口，不能直接调用 Win32、OCR SDK 或鼠标键盘库。

## 公共类型

```rust
pub type TaskId = uuid::Uuid;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Point { pub x: i32, pub y: i32 }

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Rect { pub x: i32, pub y: i32, pub width: i32, pub height: i32 }

#[derive(Debug, Clone)]
pub struct Screenshot {
    pub pixels: Vec<u8>,
    pub width: u32,
    pub height: u32,
    pub captured_at: std::time::SystemTime,
    pub fingerprint: String,
}

#[derive(Debug, Clone)]
pub struct TextBox {
    pub text: String,
    pub bounds: Rect,
    pub confidence: f32,
}

/// 一张**由操作者自己框出来**的图标模板（BGRA，行优先，与 `Screenshot` 同一套表示）。
///
/// 它来自**图标库**（`<图标库>/<名字>/<编号>.png`），`label` 是
/// **相对图标库目录**的路径（`聊天/2.png`）——一个名字底下可以有多张图，
/// 只说名字没法告诉人是哪一张坏了。
/// 程序绝不自己裁一块"看起来像图标"的区域：猜错位置、裁到空白，
/// 都会变成一次**静默的、看起来完全正常**的运行——匹配分数照样很高
/// （它匹配的就是它自己刚裁的那块），点击照样发出去，只是点到了别的地方。
#[derive(Debug, Clone)]
pub struct IconTemplate {
    pub label: String,
    pub pixels: Vec<u8>,
    pub width: u32,
    pub height: u32,
}

/// 一次图标命中的位置与分数。`bounds` 是**图像坐标系**，由调用方换算成屏幕坐标。
#[derive(Debug, Clone, PartialEq)]
pub struct IconMatch {
    pub bounds: Rect,
    pub score: f32,
    pub template_index: usize,
    pub template_label: String,
}

#[derive(Debug, thiserror::Error)]
pub enum AutomationError {
    #[error("企业微信窗口不可用或不是前台窗口")]
    ClientNotReady,
    #[error("屏幕状态在操作前发生变化")]
    ScreenChanged,
    #[error("本地视觉识别结果不确定：{0}")]
    AmbiguousVision(String),
    #[error("需要人工处理：{0}")]
    NeedsHumanReview(String),
    #[error("平台操作失败：{0}")]
    Platform(String),
}
```

## 平台端口

```rust
/// 只允许操作用户当前可见、已解锁的交互式桌面。
pub trait DesktopPlatform: Send + Sync {
    /// 启动已由用户配置且经验证的企业微信可执行文件；不得猜测路径或提权启动。
    ///
    /// **不属于任务流程**：客户端由操作者自己启动并登录，`execute()` 不会调用它。
    /// 它只服务于界面上的「启动客户端」按钮。
    fn launch_wecom(&self) -> Result<(), AutomationError>;

    /// 将已验证的企业微信窗口置于前台，并返回它在屏幕上的边界。
    ///
    /// 这是任务开始时的「接管」动作：找不到可见窗口即返回 `ClientNotReady`，
    /// 由核心层转成 `NeedsHumanReview`，绝不自动拉起客户端。
    fn focus_wecom(&self) -> Result<Rect, AutomationError>;

    /// 捕获指定屏幕区域。调用方不得传入企业微信窗口外的区域。
    fn capture(&self, region: Rect) -> Result<Screenshot, AutomationError>;

    /// 点击前验证当前前台窗口与预期窗口一致；不满足则拒绝输入。
    fn guarded_click(&self, target: Point, expected_window: Rect) -> Result<(), AutomationError>;

    /// 在 `at` 处滚动鼠标滚轮。`notches > 0` 表示向下滚动内容。
    ///
    /// 滚轮事件只送给**光标下**的窗口，所以实现方必须先把光标移到 `at`，
    /// 并和点击一样在动作前验证前台窗口与标定一致。
    fn scroll(&self, at: Point, notches: i32, expected_window: Rect)
        -> Result<(), AutomationError>;

    /// 目标窗口所属线程是否仍在处理消息。`false` 表示它已卡死。
    ///
    /// Windows 侧实现为 `IsHungAppWindow`（窗口线程超过 5 秒未取消息即判定未响应）。
    /// 这是**纯只读查询**，不改焦点、不产生输入，因此不受前台守卫约束。
    /// 尚未定位到窗口时返回 `ClientNotReady`。
    ///
    /// 它与"画面有没有变化"是互补的两条判据：画面比对抓不住
    /// "主线程死锁但界面仍在刷新"之外的边角情形，系统级判据也抓不住
    /// "线程活着但滚不动"的假死，两条都要。
    fn is_responsive(&self) -> Result<bool, AutomationError>;

    /// 将文本写入剪贴板并粘贴到当前已聚焦控件；完成后清除临时剪贴板内容。
    fn paste_text(&self, text: &str, expected_window: Rect) -> Result<(), AutomationError>;

    /// **逐字**把文本敲进当前已聚焦控件（不走剪贴板）。
    ///
    /// 与 `paste_text` 是两条路，**不能互相替代**：
    ///
    /// - 搜索框必须逐字输入。整段粘贴是一次性事件，客户端的联想框收不到
    ///   "正在打字"的过程，下拉列表根本不会出现；
    /// - 逐字输入还会按字符间隔放慢（`typing_interval_ms`），
    ///   否则联想请求互相打断，下拉里可能停在一个中间状态。
    ///
    /// Windows 侧实现为 `KEYEVENTF_UNICODE` + `SendInput`，按 UTF-16 码元发。
    /// ⚠️ 代理对（emoji、部分生僻字）**必须拆成两个码元**，一次发一个。
    ///
    /// 同样受前台守卫约束：动作前后都校验 `expected_window`。
    fn type_text(&self, text: &str, expected_window: Rect) -> Result<(), AutomationError>;
}
```

## 视觉端口

```rust
pub trait LocalOcr: Send + Sync {
    /// 仅对内存中的局部截图推理，禁止网络上传与远程推理。
    fn recognize(&self, image: &Screenshot) -> Result<Vec<TextBox>, AutomationError>;
}

pub trait ContactMatcher: Send + Sync {
    /// 返回唯一且满足最低置信度的完全匹配项；同名或模糊匹配必须返回错误。
    fn find_unique_exact_match(
        &self,
        expected_name: &str,
        candidates: &[TextBox],
        min_confidence: f32,
    ) -> Result<TextBox, AutomationError>;

    /// 「这一个候选行不行」。与上面的「在候选集里挑一个」必须对同一个名字给同样的答案。
    fn accepts(&self, expected_name: &str, candidate: &TextBox) -> bool;
}

/// 图标定位端口：在一帧**局部截图**里用模板匹配找出一个小图的位置。
///
/// 与 `LocalOcr` 的分工很清楚——OCR 回答"这一片文字写的是什么"，
/// 本端口回答"这个图标在哪儿"。
pub trait IconLocator: Send + Sync {
    /// 输入打包成 [`IconQuery`]，不写成三个参数：模板、阈值、期望位置
    /// 是**一起被决定**的，参数表越长越容易在某个调用点漏掉一项——
    /// 而漏掉先验不会报错，只会静默退回"取最高分"。
    ///
    /// `query.templates` 为空 ⇒ **必须报错**，不得当成"没找到"静默通过。
    /// 最高分低于 `query.min_score` ⇒ `AmbiguousVision`（转人工），
    /// 不得返回一个"分数不高但先用了"的结果。
    fn locate(
        &self,
        frame: &Screenshot,
        query: &IconQuery<'_>,
    ) -> Result<IconMatch, AutomationError>;
}

/// 一次图标匹配的输入。
pub struct IconQuery<'a> {
    pub templates: &'a [IconTemplate],
    /// 最高分低于它转人工。见 [`IconLocator::locate`]。
    pub min_score: f32,
    /// 期望命中位置。`None` = 不做位置先验，取最高分。
    pub prior: Option<IconPrior>,
}

/// 位置先验：**越靠近导航区中心的命中越可信**。
///
/// 左侧导航栏是一列纵向排列、彼此长得很像的线性图标。逐张模板取最高分时，
/// 偶尔会出现"旁边那个图标得分略高一点"——而点错图标的代价是后面整条流程
/// 都作用在错误的视图上，比直接失败严重得多。
///
/// ⚠️ **先验绝不能把低分命中抬上来。** 只用"离中心最近"会引入更坏的缺陷：
/// 一个 0.82 分的噪声命中恰好压在中心上，就能把 0.99 分的正确命中挤掉。
/// 所以先验只在**分数本来就相近**时才参与决策——见 `score_tolerance`。
pub struct IconPrior {
    /// 期望的命中位置，位于**传入截图的图像坐标系**（与 `IconMatch::bounds` 同一套语义）。
    pub at: Point,
    /// 位置先验生效所需的分数容差。
    ///
    /// 只有分数不低于「最高分 − 本值」的候选才有资格参与位置比较；
    /// 高分段里一个都没有时，退回"取最高分"。
    /// 取 0 等于关掉先验（只有并列最高分才会看位置）。
    pub score_tolerance: f32,
}
```

## 实现禁止项

- 不得使用客户端内存读取、注入、Hook 或逆向接口；
- 不得在 `DesktopPlatform` 内隐藏网络发送、定时发送或重试发送；
- 不得根据相似度“猜测”联系人；
- 不得绕过权限提示、验证码、登录或风控限制；
- 不得把 `Screenshot`、`TextBox`、任务正文上传到远程服务。

## 标定预览：只读旁路之一

`WindowsDesktop::preview()` 是**固有方法，不在 `DesktopPlatform` trait 上**。
它是上面"只能依赖端口"这条规则的例外，理由如下：

- 它不参与业务流程，只服务于界面的标定（区域、图标模板），返回 `(Rect, Screenshot)` 供显示；
- 它**不改变焦点**——与 `focus_wecom` 的关键区别。标定只需要"看一眼窗口长什么样"，
  而 `SetForegroundWindow` 在 Windows 前台锁定策略下经常被拒绝（调用方自身不在前台时），
  做成"先聚焦再截图"会让这个功能时灵时不灵；
- 它不点击、不粘贴、不发送、不写剪贴板，因此不产生任何对外副作用；
- 它仍然受资源上限约束（`preview_max_pixels`），窗口矩形是外部数据，
  不能拿它直接分配内存。

把它放进 trait 会迫使每个平台适配器（含 mock）都去实现一个与业务流程无关的
展示用方法，得不偿失。IPC 命令层本来就是组合根，允许按平台条件编译直接引用
`platform-windows`。

送进界面前会等比缩到 `PREVIEW_MAX_WIDTH`：区域叠加层用的是百分比，
与图像实际像素尺寸无关，所以缩小不影响标定精度，却能把 4K 窗口的
IPC 载荷从几十 MB 压到几百 KB。

> ⚠️ **缩过的图只能给人看，不能当模板。** 图标模板必须回到原始分辨率去裁
> （见下面「图标库」一节），所以 `save_icon_from_crop` 会按框**重新截一张**，
> 而不是从预览图上裁一块下来。

### 命令层的三条刻意的约定

**一、不按运行模式设限。** 标定属于**配置**而不是执行：它只读地看一眼目标窗口，
不点击、不输入、不发送，跟本次任务跑演练还是跑真实无关。而且实际使用顺序往往是
"先把窗口和要用的区域标定好，再决定用哪种模式跑"，卡在模式上只会让人没法做准备。
（`click_icon` 会产生真实点击，但它同样不设限——它是**人按的按钮**，
不是任务流程的一步。界面上用两次点击确认来兜住这一点。）

**二、窗口类名由调用方传入，不读已保存的配置。** 界面上显示的是**草稿**，
用户改了类名但还没点「保存配置」时配置里仍是旧值。如果这里读配置，就会报出
"界面上明明写着新类名，截图却说找不到窗口"这种自相矛盾的错——调用方传进来的
就是用户此刻看到的值，两边不可能不一致。

**三、`start_task` 的「本次走哪条路」由请求传入，不读也不写配置。**
**模式**（演练 / 真实）、工作流、导航目标都是**运行参数**（`RunChoice`），
随 `StartTaskRequest.run_choice` 下发，**必填、后端没有兜底**：
缺了直接反序列化失败，而不是悄悄退回配置里的默认值。

这条是 2026-09-19 那个 bug 的修复：界面上把工作流切成别的、连跑三条任务，
三条 `task-*.log` 里记的全是 `SearchContact`。根因就是**两处真相**——
界面改的是草稿、命令层读的是已保存的 `state.config`，而"没点保存"这件事
看起来跟"选工作流"毫无关系。改成运行参数之后：界面选的与真正跑的是同一个值，
不用先保存，也**不会写进 `config.json`**（用户明确要求"这个不要保存"）。

★ **模式是同一轮里跟着改的**，用户原话：「「模式」（演练 / 真实）也改成读界面的
选项，配置里只做为默认值加载」。它比工作流多绕一圈——不只决定用哪一组端口，
还决定**要不要带标定窗口**（演练模式跑替身窗口，没有"真实窗口尺寸"这回事）
与**审计里记哪个平台**。做法是在 `build_runner` 的**第一件事**就把模式并进配置副本
（`config.mode = choice.mode`），后面所有判断照旧读 `config.mode`，**判据只有一处**。

⚠️ 由此带来两处界面上的连带改动，改界面时别踩回去：

- 模式下拉**绑 `runChoice.mode`**，与工作流同款：**不进草稿、不置 `dirty`**。
  页头那个模式徽标、`canSave` 的区域校验、演练场景选择器的显隐，
  一律看 `App` 算出来的 `activeMode`（`runChoice.mode ?? info.config.mode`）——
  **不能用 `draft.mode`**。
- `RuntimeInfo.notice`（单句）改成了 **`mode_notices`（演练 / 真实各一句）**。
  模式是运行参数，只发一句就得在"界面选的"和"配置存的"里选一个，
  而选错的方向恰好是最危险的那个（提示说"演练"、实际在动真窗口）。

⚠️ `RuntimeConfig.mode` / `.workflow` / `.nav_target` 这三个字段**还在**，但它们只是
**界面打开时的初始值**——装配期不再读它们。改它们不影响任何任务。
（例外：点「保存配置」时会把**当前选的模式**一并记成下次的默认值，
否则"上次用的模式"就再也不会被记住。）

★ `nav_target` 的值域是**图标库里的目录名**（`data/icons/` 下一级目录），
`RunChoice.nav_target` 与 `RuntimeConfig.nav_target` 都是 `string`。
界面上那个下拉**读图标库**（`listIcons()`），不是一份写死的清单——
**别改回去**：写死的时候图标库里四五个图标在下拉里选不出来，也对不上。
详见 `docs/todo.md` T26。

### 「要填什么」也是按工作流算的（T27）

**「外部联系人名称」与「消息正文」不是永远必填**：它们由 `workflow_inputs(workflow)`
（`src-tauri/src/runtime/requirements.rs`）按**本次选的那条路**决定，
随 `workflow_requirements` 以 `needs_contact` / `needs_message` 下发给界面。

- 命令层按它决定要不要拒绝空值；`TaskForm` 按它决定那两个框**显不显示**、
  「开始任务」能不能点。**判据只有一处**——各写一份的话，分叉的表现是
  「界面说齐了、点开始却被拒」，或者**「按钮点不动、也不说为什么」**。
- ★ 界面**拿不到**判据（还没问到 / 请求失败 ⇒ `null`）时**一律放行**，
  交给命令层去拒绝并给出原因：**拒绝是看得见的，点不动是看不见的**。
- 「只做导航」整块输入都不显示（留着填了也没用的框，下一个人还会去填它）。

⚠️ 由此带来的现象：这条路跑出来的任务，`external_contact_name` 与 `text` 都是空的。
那是**如实反映**（这条路不找人、也发不出消息），不是漏填——日志里写
「（不适用：只做导航）」，界面上写「（这条工作流不找人）」（`taskDisplay.ts`）。

## 面向操作者的准备命令

这些命令都只做**准备**，都不属于任务流程。它们分成两类。

### 只读的（不点击、不输入、不发送）

| 命令 | 作用 | 副作用 |
|---|---|---|
| `pick_target_window` | 倒计时内读**光标下**的窗口（类名 / 标题 / exe） | 无 |
| `record_window_geometry` | 只读量出目标窗口尺寸 + DPI，作为标定尺寸 | 无 |
| `preview_target_window` | 截一张窗口预览图，供界面标定与图标框选 | 无 |
| `probe_nav_icon` | 在当前画面上试一次图标模板匹配，报出**分数与位置**（收的是**图标名**，一个名字下的每张图都量一遍） | 无 |
| `list_icons` | 列出图标库里的图标（名字、**全部变体**、缩略图） | 无 |
| `save_icon_from_crop` | 把预览图上框出来的一块存成图标模板（同名 = **补一张变体**） | 无 |
| `list_calibration_plan` | 读出**界面标定计划**：有哪些界面要标、每项框哪儿、当前标到哪一步 | 无 |
| `validate_area_mark` | 校验一个标定框：key 认不认识、矩形合不合法。**纯校验，不改状态** | 无 |
| `workflow_requirements` | 读出**三条工作流各自要求先标哪几块区域**、当前标了没有（收的是**草稿**配置） | 无 |

只读的那一组**不按运行模式设限**：它们跟这次任务跑演练还是跑真实无关，
实际使用顺序也往往是"先把窗口、区域、图标都标定好，再决定用哪种模式跑"。

`workflow_requirements` 存在的**全部理由**是让界面不必自己列一张
"哪条工作流要哪几块"的表：那张表和装配期用的判据一旦不一致，
表现就是「界面说齐了、点开始却被拒」，而人只会去怀疑标定本身。
所以它和 `build_runner` 的拒绝判据共用同一个函数（`runtime::required_marks`），
用例 `ipc_flow.rs::the_requirement_list_matches_what_assembly_enforces`
就是拦这个的。它取**草稿**配置，理由同下面的"窗口类名由调用方传入"。

### 会产生副作用的（由人明确按下）

| 命令 | 作用 | 副作用 |
|---|---|---|
| `launch_client` | 启动用户配置的客户端可执行文件 | 启动一个进程 |
| `register_capture_hotkey` | 注册「一键截屏」全局热键（四个修饰键勾选 + 一个主键） | **占一个全局热键** |
| `unregister_capture_hotkey` | 注销它。**幂等**——没注册时也返回成功 | 释放热键 |
| `delete_icon` | 删除图标库里的**一整个图标**（含它的全部变体） | 删一个目录 |
| `delete_icon_variant` | 删除一个图标里的**某一张**图 | 删一个文件 |
| `click_icon` | 定位一个图标并**真的点它一下** | **产生鼠标点击** |
| `draw_cursor_circle` | 让光标以**当前所在位置**为圆心沿圆周走一圈（半径 = 本程序窗口短边的一半） | **移动光标**（不点击、不输入、不抢前台） |

这三个同样**不按运行模式设限**：运行模式决定的是"任务怎么执行"，
不是"人能不能动手"。但界面上必须写明它会真的产生输入——`click_icon`
的按钮做成**两次点击确认**（第一次"上膛"、第二次才真的点），
就是因为它会在对方的聊天客户端上产生真实动作；删**整组**图标也是两次
（一次丢掉的可能是好几张人对着屏幕框出来的图），而单张的「删除这张」
只丢一张、不加确认。

⚠️ `register_capture_hotkey` / `unregister_capture_hotkey` 的副作用**在本机，不在客户端**：
它占的是一个全系统热键，**不向任何程序发送输入**，也不会把窗口带到前台。
所以它不需要两次确认——但它**必须被还回去**：界面进标定页才注册、离开就注销，
程序启动时不占用。理由与三种触发方式的取舍见下面「截图的三种触发方式」。

- `pick_target_window` 必须**轻**：倒计时期间每 200ms 采样一次（5 秒 = 25 次），
  所以它**不截屏、不编码**——这是它与 `preview_target_window` 的关键区别，
  后者要截屏 + 缩放 + PNG + base64。`is_self` 用**可执行文件路径**判定，
  不用 PID（PID 每次启动都变）。
- `launch_client` 的 exe 路径与 SHA-256 由界面传入，**不读已保存配置**（同上的草稿理由）。
  路径为空直接拒绝。它**不会**被 `execute()` 调用。
- `record_window_geometry` 走 `WindowsDesktop::measure()`——同样是固有只读方法，
  **不截屏也不聚焦**，因此不会把用户的窗口抢到前台。空类名直接拒绝，
  否则会退化成"匹配任意窗口"。
- `draw_cursor_circle` 是**演示**，不是只读命令，但它也不属于任务流程：只移动光标，
  不点击、不输入、不抢前台，所以在演练模式下照样能用，也**不需要两次确认**。
  ★ 界面上它**必须先倒计时再调**（`CursorMotionPanel.tsx`，3 秒）：命令是同步跑完
  整圈才返回的，没有倒计时的话点下去像"卡住了"；倒计时同时给了操作者把鼠标挪到
  想当圆心的位置的时间。**圆心取的是调用那一刻的光标位置**，不是按钮的位置。
  ★ **它不收速度参数**：光标速度只在后端有一处定义（平台层 `WindowsDesktopConfig`
  的默认值，也正是任务里用的那个）。让界面传值就等于在 TS 里再抄一份默认值，
  以后改了会两边对不上而**两边都看不出来**。详见 `docs/todo.md` T24。
- `probe_nav_icon` 与 `save_icon_from_crop` 都取**草稿**参数，并且
  **模板载入走的是与任务装配同一个函数**——否则按钮报出来的分数与任务里
  真正会用的那些图不一致，标定就白做了。

### 截图的三种触发方式：为什么必须有「延时」和「热键」

标定「搜索下拉列表」这类区域会撞上一个死结：**客户端里的搜索下拉框是失焦即收的临时弹层**，
而「截图并标注」这个按钮本身就要求操作者把鼠标点到本程序的窗口上——这一点下去，
前台就转到了本程序，弹层在**按下的那一刻**已经收起。等截屏真正执行时，截到的是收起后的画面。

★ 关键区分：**截屏这一步是无辜的**。`preview_target_window` → `WindowsDesktop::preview()`
→ `winapi::capture_region()` 全程只读，`preview()` 的文档注释里写死了
「不改变焦点、不产生任何输入事件」。收掉下拉框的是**点击按钮**这个动作，不是截屏。

三条推论就是这三种触发方式存在的理由：

| 触发方式 | 做法 | 什么时候用 |
|---|---|---|
| 立刻截 | 点按钮 → 马上截 | 常驻画面（主界面、联系人列表、聊天记录）——聚焦与否长得一样 |
| 延时截 | 点按钮 → 倒计时 8 秒 → 自动截 | 临时弹层。操作者利用这几秒切回客户端把画面摆出来 |
| 热键截 | 画面已摆好时按组合键 → 后端发事件 → 界面截 | 同上，但**不必把前台让出来**，也不用等 |

**「不是所有截图都有这个问题」的真正原因**：只有失焦即收的临时弹层会这样。主窗口、列表、
聊天区在聚焦与不聚焦时长得完全一样，所以那几张永远没事。症状看着像「时灵时不灵」，
实际是「弹层 100% 必挂、常驻画面 100% 没事」——按这个判据就能一眼分出是哪一类。

**热键为什么只发事件、不自己截图**：截哪张图取决于界面上**当前正在标定哪个界面**、
以及配置**草稿**里的窗口类名——这两样只有界面知道。后端若去读已保存的配置，就会出现
「界面上明明写着新类名、截出来的却是旧窗口」。所以后端只说一句「可以截了」
（事件 `calibration://capture-hotkey`），实际截图仍走界面已经在用的 `preview_target_window`。

**热键的两个硬约束**：

- **必须带至少一个修饰键**。裸按键一旦注册成功，那个键在整个系统里就都被本程序截走了——
  注册一个「全局 A」会让用户在**任何**程序里都打不出 a。后端直接拒绝，不做兜底。
- **是全局资源，必须还回去**。界面进标定页才注册、离开就注销（`CaptureTrigger` 的卸载清理），
  程序启动时不占用。所以**切到别的页签会自动停用**——这不是 bug，是不长期霸占系统热键。

⚠️ 延时倒计时**期间不要最小化本程序窗口**：WebView2 在窗口最小化时会把定时器降频，
到点会晚一些。判据用的是**截止时刻**而不是累加值，所以最多晚一个刷新间隔，不会越走越慢。

⚠️ 截图范围严格是**目标窗口的矩形**（`window_rect` → 屏幕 BitBlt）。所以：超出窗口边框的
弹层会被**裁掉**，被别的窗口盖住的部分会是**黑的**（刻意如此，工具不猜内容）。
标定这类画面时先让目标窗口完整露出来。

## 界面标定

「界面标定」页要回答的是「这个界面里，哪一块是我要的」。标定结果落进配置，
供后续编排读取——**标一次，之后每次任务都按它走**。

坐标存**相对窗口的比例**（`[x, y, w, h]`，0–1），不存像素：窗口挪动、
换分辨率都不用重标。⚠️ 但**窗口尺寸变了标定就失效**——左侧图标栏、头像列是
固定像素宽的，同一份比例换到另一个尺寸下会落到别处（见 `docs/todo.md` T2）。

因此任务启动时会核对窗口尺寸：**不符就自动把窗口调回标定尺寸**，
调不动（客户端有最小尺寸限制）才转人工。想**换一个**窗口尺寸，就得重标 + 重记尺寸。

### 4 个场景、14 个标定项

清单在 `calibration/catalog.rs`，**只有这一处**；界面把它当数据渲染。

| 场景 | 截图前把客户端切成什么样 | 标定项（加粗 = 必填） |
|---|---|---|
| `main` 主界面 | 停在主界面：左侧竖排导航图标、顶部搜索框、下面会话列表，右侧内容展示区 | 1.1 导航区 / 1.2 搜索框区 / **1.3 列表区** / 1.4 右侧内容展示区域 |
| `history` 历史对话 | 点开一个历史对话 | 2.1 搜索框区 / 2.2 对话历史列表区域 / **2.3 对话标题** / **2.4 对话内容** / **2.5 发送消息输入框** / 2.6 发送按钮 |
| `contacts` 联系人列表 | 点导航区的「联系人」图标切过去；**先点一个联系人**让资料面板显示出来再截图 | 3.1 搜索框区 / 3.2 联系人列表区域 / 3.3 联系人资料区域 |
| `search_dropdown` 搜索下拉列表 | 点开搜索框让下拉列表弹出来（输入框里留个词，别清掉） | 4.1 下拉列表区域 |

**必填的四项就是编排层在读的那四个 `regions` 具名字段**，只是换了位置出现在场景里。
只有它们 `required: true`（如实反映 `build_runner` 在真实模式下的检查）；
其余标成 `false` 是**如实反映现状**——它们还没有编排代码在读，
硬标成必填只会让人以为「不标就跑不了」，然后去标一堆用不上的框。

**按界面状态分组不是分类癖**：一块区域只有在它所在的界面显示出来时才能标——
搜索框在下拉面板没打开时根本不在画面上。所以流程只能是「切到某个界面 →
截一张图 → 在这张图上框出这个界面的全部区域」，而引导语也必须说清
「现在应该看得见什么」，而不是「切到搜索页面」这种说了等于没说的。

### 三处「搜索框」不是同一个框

主界面 / 历史对话 / 联系人列表各有一个搜索框（`main_search` /
`history_search` / `contacts_search`）。它们**必须分别标**：客户端里这是三个
不同位置、不同尺寸的控件，用同一份坐标去点，另外两个必然点空——
而点空的症状只是「点了一下没反应」。

⚠️ **搜索式工作流用的是 `main_search`（主界面那个）**，不是另外两个。
它走的是「在主界面上搜人」，不是在历史对话里搜消息。

### ★ 搜索式工作流要的三块区域，分散在**三个不同场景**里

这是最容易漏的一处——它们不在同一个页面上，必须**逐个场景切过去标**：

| 标定项 | 属于哪个场景 | 截图前要把客户端切成什么样 |
|---|---|---|
| `main_search` 搜索框区 | `main` 主界面 | 停在主界面 |
| `search_dropdown` 下拉列表区域 | `search_dropdown` 搜索下拉列表 | 点开搜索框让下拉弹出来，输入框里留个词 |
| `contact_profile` 联系人资料区域 | `contacts` 联系人列表 | 点导航区「联系人」图标切过去，**再点一个联系人**让资料面板显示出来 |

所以「四个场景 14 项」对搜索式来说不是可选项——**四个场景里有三个都要标**，
只标主界面是跑不起来的。没标全时装配期会拒绝，并列出缺哪几块
（用界面上的说法，比如「搜索框区」，不是 `main_search`），
而且**不会在任务列表里留下记录**。

不想自己记这些依赖的话，界面上直接读 `workflow_requirements`——
它下发的就是这张表（判据只有一处，见上面「只读的」那一节）。

### 两套编号，别混

- **清单编号**（`1.3`、`2.5`）：按 `SCENES` / `ITEMS` 的顺序。界面左边列表的
  色块和画布上框的角标显示的是它，`docs/` 里说「2.4」也指它；
- **探针编号**（`1`~`4`）：`screen_probe annotate` 按 `CoreRegion` 的固定顺序
  画在**命令行截图**上的角标。界面上只在**当前项**那里显示（「截图角标 N」）——
  14 行每行再挂一个号会挤得看不清，而它真正用到的场合只有一个：
  对着截图说「把 3 往左挪」的时候。

两者不是一回事：四个核心区域分散在两个场景里（`list_area` 在主界面、
另外三个在历史对话）。⚠️ `CoreRegion::probe_index` 的顺序**必须与
`automation_core::DEFAULT_REGIONS` 一致**，否则操作者照着截图说的话会对错区域。

### 坐标存在哪

分两处存，**归属由后端声明**（`calibration::ITEMS` 里的 `storage`）：

| 存哪 | 谁 | 为什么 |
|---|---|---|
| `regions`（四个具名字段） | 1.3 列表区 / 2.3 对话标题 / 2.4 对话内容 / 2.5 发送消息输入框 | 编排层按名字直接读（`RegionConfig::to_runner_regions`），存储结构与读取路径都不能动：它们有默认值，且真实模式下缺一不可 |
| `area_marks`（字典，键 = 标定项 `key`） | 其余 10 项 | 见下 |

**`area_marks` 为什么是字典而不是又一组具名字段**：标定项会随流程完善而增长，
每加一项都要动 Rust 结构体、TS 类型、界面元数据表三处，漏一处**不报错**——
只表现为"界面上少一个入口"，或者"多一个永远存不进去的框"。现在清单只有
`calibration/catalog.rs` 一处，界面把它当数据渲染。

**`area_marks` 里的项没有默认值**：`None` 就是「还没标」。给一个猜出来的默认值，
症状会是「任务照常跑完，只是点到了别的地方」——本项目最不能接受的一类失败。

**每一项都记下标定时的 `window` 几何**：比例本身跨尺寸可用，但界面元素不是。
记下"这一份比例是在多大的窗口上量的"，才回答得了"这个框还能不能用"。

**框的值以草稿为准，不以计划为准**：`list_calibration_plan` 返回的是
打开这一页那一刻的快照，拖完框就过期了。清单与说明用它，画布与进度从草稿现读——
两处都当权威的话，拖完框界面会跳回去。

### 失效的标定项，以及那个「出口」

清单会随流程完善而改（改名、拆并、删项），而配置是**持久化**的：清单改过之后，
旧 key 就留在了 `area_marks` 里。它们**不会被任何流程读到**，**却会挡住保存**——
落盘前的兜底校验拒绝未知 key。

于是升级到新清单的人会卡在「一保存就报错，但界面上找不到那个项」：
报错说得没错（那个键确实没人读），可**没有出口**。

所以有这一对：

- `calibration::stale_keys(config)` —— 列出「配置里有、清单里没有」的键，
  顺序取自 `BTreeMap`（按 key 排序，稳定），随 `CalibrationPlan.stale_keys` 下发；
- `prune_stale_marks` 命令 —— 清掉未知键，**立刻落盘**，返回清掉的个数。

界面在标定页顶部显示一条红色提示条，写明是哪几项、为什么挡住保存，
旁边一个「清理这几项」按钮。

⚠️ 清理时**两件事都要做**：服务端要清（它才是让保存失败的那一份），
**草稿也要清**——只清服务端的话，用户接着点「保存配置」，
草稿里那些键又被原样写回去，报错照旧。界面按后端下发的 `plan.stale_keys`
决定删哪几个，不自己扫草稿：哪几个键算失效由清单说了算，前端再判一次就是第二个判据。

**为什么它直接落盘、而 `validate_area_mark` 只校验**：`validate_area_mark` 挡的是
「用户正在拖的这一个框」，它必须留在草稿里，否则 `dirty` 与「保存」按钮都失去意义
（见 `docs/todo.md` T12）；而 `prune_stale_marks` 清的正是让保存失败的那些键，
只改内存的话用户下一次点「保存」仍然会被自己挡住。两条写入路径都走
`persist_config`，所以「落到盘上的配置一定过了校验」只有一处实现。

⚠️ **校验走哪条路**（2026-09-18 晚改）：界面是**草稿式**保存的——拖框只改
前端 `draft`，点「保存配置」才落盘。所以校验**不**做成"拖一下就把框写进服务端配置"，
而是：

- 松手时调 `validate_area_mark(key, rect)` 问一次（`RegionCanvas` 的 `onCommit`，
  与每帧都触发的 `onChange` 分开，免得自己防抖）；
- 不合法**只提示、不把框弹回去**——弹回去会让人以为拖动失灵了；
- `set_runtime_config` 落盘前**兜底再校验**一遍 `area_marks`，
  界面上那条路挡不住手改配置文件。

两条校验（`find_item` 拒未知 key、`validate_rect` 复用
`RelativeRegion::validate`）**都在 `calibration` 里，只此一处**。
为什么不是"加两个写配置的命令"见 `docs/todo.md` T12——
那样会绕过草稿，`dirty` 与「保存」按钮就都没意义了。

⚠️ `area_marks` 在 TS 里声明成**可选**（`area_marks?`）：后端那个字段带
`#[serde(default)]`，老配置文件里没有这个键，读到的会是 `undefined`。
读的地方一律 `area_marks ?? {}`，**别补默认框**。

⚠️ 同一个区域**两处可编辑**：标定页（拖框）与「任务」页里的
`RegionCalibration`（直接填百分比）。两处改的都是同一份草稿的 `regions`，
所以不会不一致；但**名字必须一字不差**——两边不一致不会报错，
只会让同一条区域叫两个名字，看起来像两个不同的地方。
`RegionCalibration.tsx` 里那四条标签是**手抄**的（TS 读不到 Rust 常量），
改 `calibration/catalog.rs` 时要一起改。见 `docs/todo.md` T13。

## 图标库

图标库里存的是「从真实画面上框出来的一个小图标」，**一个图标名 = 一个目录**
（`<图标库>/<名字>/1.png`、`2.png`…），目录里可以放**多张**图。
它是导航图标那一步的**前提**：图标上没有文字，OCR 读不到，只能靠模板匹配，
而模板只能由人框出来。

### 一个名字为什么要能存多张

同一个图标在**选中 / 未选中 / 带气泡提醒 / 气泡里数字不一样**时长得都不一样，
而它们指的是**同一个**图标。只存一张的后果很具体：点完图标界面会停在这个视图上，
图标随之变成选中态；下一次跑的时候画面上是选中态，而库里只有未选中那张
⇒ 再也匹配不上。

配置里引用的是**名字**（`nav_icon_templates`），载入时才展开成那个名字下的全部图。
这样以后补一张变体不必回配置页重勾一次——而漏勾**不报任何错**，
只表现为"某个状态下匹配不上"。

**保存时填同一个名字 = 给这个图标补一张**，不是重名错误。文件编号取
"当前没被占用的最小正整数"，不重排已有编号。

### 图标库放在哪

默认在**数据目录**下的 `icons/`（`icon_library::default_dir`），
不是 AppData：AppData 底下那层目录名是包标识符（`com.example.wecom-local-rpa`），
没人记得住，找一次要翻半天；而图标模板是**人对着屏幕一张一张框出来的素材**，
找得到、备份得了才算数。

位置可以在界面上改（`RuntimeConfig.icons_dir`，留空 = 默认）。写**相对路径**时
挂在**程序运行当前路径**上（例如 `data/icons`），与数据目录同一条规则——
基准取 `data_dir::working_dir()`，**不在这里另写一次 `current_dir()`**。

这里**曾经**用编译期的 `CARGO_MANIFEST_DIR` 往上找 workspace 根，好处是
「不管从哪儿启动都落在仓库里」。换成运行期的当前路径是有意的取舍：
那种做法在二进制被拷到别的机器上跑时会**静默失效**——往上找不到 `[workspace]`，
于是悄悄退回数据目录；而图标库找错了地方不报任何错，只表现为列表空着。
现在它与配置文件、任务日志、证据图**同在一处**，界面上也显示得出来，
找错了一眼能看见。

### 名字为什么要卡得这么严

名字会被拼成**目录名**，所以 `icon_library::validate_name` 拒绝：

- **路径分隔符与保留字符**——名字一旦能带 `\` 或 `..`，「保存图标」就变成了
  「往任意路径写文件」；
- **结尾的点**——Windows 建目录/文件时会**静默**去掉它，于是"保存成功"之后
  按原名再也找不到它，症状是「明明存了却说没有」；
- **保留设备名**（`CON` / `NUL` / `COM1` …）——带上扩展名也建不出来，
  报出来的是没头没尾的「系统找不到指定的文件」。

规则只在**一处**实现，命令与界面都走它。

`delete_icon_variant` 是**删除**命令，它的 `relative` 来自界面，因此额外校验
"图标库目录下、且属于这个名字"，路径由校验过的名字重新拼——不然一个
`..\..\重要文件.png` 就能删掉磁盘上任何东西。

### 为什么框选之后要重新截一张

`save_icon_from_crop` 收的是**预览图坐标系**里的框（`rect` + `preview`），
但它**不从预览图上裁**：预览是缩放过的（Triangle 滤波），裁出来的模板
边缘会带上插值出来的杂色，拿去匹配原始分辨率的真实画面自然对不准——
而且分数不会低到让人起疑，只表现为「图标明明在，就是匹配不上」。
所以它按框重新截一张原始分辨率的窗口画面再裁。

代价是必须确认两次截图之间窗口尺寸没变（否则换算比例失效、框会落到别处）。
判据用的是**同一个缩放函数**算出来的期望尺寸，不是另写一份比例公式。

写完立刻用任务装配时的同一个载入函数验一遍；不可用就**把文件删掉**再报错——
图标库里只允许留能用的模板。留下的坏模板会以"分数很低"的形式在任务里发作，
而那时人只会去怀疑阈值。

### `probe_nav_icon` 为什么绕过阈值

`IconLocator::locate` 把"分数不够"变成一个错误（`AmbiguousVision`），这对任务是**对的**：
任务只需要"过/不过"。但标定需要的恰恰是**分数本身**——"0.62 差多少""哪张模板分高"
这些信息在"过/不过"的结论里全丢了。所以这个命令直接调 `vision::match_template`，
把分数、位置、命中的是哪张模板一起报出来，并附一个 `accepted` 表示是否过阈值。

**没过阈值也照样返回位置**，这是刻意的：那个位置是"它认为最像的地方"，
对着预览图看一眼就知道是模板截错了还是搜索区没盖住图标。只报"没找到"的话，
操作者手里就什么线索都没有。

这是**唯一**一处绕过判据的地方，且它只读、不参与任务流程。
编排层仍然只问 `IconLocator`，判据仍然只有一处。

`click_icon` 则相反：它**硬走 `IconLocator`**，分数不够直接报错且**一次点击都不发**。
这个按钮问的是"这张模板能不能用"，"分数不够但先点了"正好是最不能接受的结果。

### `click_icon` 的判据与任务里那一步**刻意不同**

同一个动作（点导航图标），但结论不一样：

- **任务里**（`NavigatingToView`）：点击后画面没变只记一条警告，**继续往下走**。
  因为"界面本来就停在这个视图上"与"点击真的没生效"在画面上分不出来，
  而前者是最常见的场景（上次跑完就留在这个视图上）⇒ 硬失败会变成"第二次跑必然失败"。
  判定交给下一步只读的 `locate_contact`。详见 `docs/todo.md` T11。
- **这里**：如实回报 `changed`，不做任何收敛。按按钮的人要的就是
  "这一下到底有没有生效"，把两种可能都写进 `notice` 让他自己判断。

> 为什么这些都要做成命令而不是命令行脚本：操作者日常用的是界面。
> 命令行探针（`screen_probe`）只配当诊断工具，用户已明确否掉"让操作者跑脚本"的形态。
>
> 探针里对应的是 `screen_probe template`（截图标模板）与 `screen_probe findicon`
> （量分数）——它们是**排查用**的，界面上的按钮才是操作者的日常路径。
