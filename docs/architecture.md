# 企业微信本地视觉自动化：总体架构

## 1. 目标与边界

本项目是一个运行于用户桌面的辅助工具：在已登录的企业微信桌面客户端中，通过**本地屏幕截图、OCR、鼠标、键盘与剪贴板**完成一对一外部联系人消息发送。

当前阶段支持 Windows 与 macOS 上的单条纯文本任务，且每次发送均要求操作者在本机明确确认。

本项目不做以下事情：

- 不调用企业微信服务端 API；
- 不修改、注入、逆向或读取企业微信客户端内存；
- 不注入进程、不挂键盘钩子、不读取按键内容。标定页的「一键截屏」热键走的是
  `RegisterHotKey`——系统在组合键命中时向本进程投递一条 `WM_HOTKEY`，
  全程不碰别的进程（见 `docs/windows-mvp-interface.md`「截图的三种触发方式」）；
- 不处理验证码、风控提示或登录异常；
- 不做无人值守批量发送、自动加好友或自动回复；
- 不将截图、联系人姓名或消息正文上传到云端。

遇到联系人无法唯一确认、OCR 置信度不足、窗口状态异常或平台提示限制时，任务必须停止并进入人工处理状态。

## 2. 架构原则

1. **本地优先**：图像、OCR 模型、任务数据与审计记录均在设备本地处理。
2. **平台隔离**：业务流程不依赖 Windows/macOS 的具体输入或截图实现。
3. **先验证、后操作**：每次可能影响收件人的操作前都需要可观测证据。
4. **默认安全失败**：不确定即失败；绝不根据模糊 OCR 结果向候选联系人发送。
5. **全程可审计**：记录任务状态、操作者确认、非敏感诊断信息与脱敏证据。

### OCR 适配器的实际形态

`vision::LocalOcr` 只规定契约：吃内存中的局部截图，吐 `TextBox`。
仓库里落地的实现是 `ExternalOcr`——它把截图编码成 PNG 通过**标准输入**交给一个
外部子进程，从**标准输出**读回 JSON 数组。子进程路径由使用者显式配置
（`ocr_command`），不在代码里猜。

仓库自带 `tools/winocr`，用 Windows 自带的 `Windows.Media.Ocr` 实现该契约：
完全离线、不需要下载第三方模型。要换成 PaddleOCR 只需提供满足同一契约的可执行文件，
核心层与界面都不需要改动。

`winocr` 的两个已知限制（影响策略有效性，不要忽略）：

- 引擎对中文**按字切词**，会把「张三」输出成「张 三」。工具内已做 CJK 空格归并，
  少了这一步逐字精确匹配与送达核验都会失败；
- 引擎**不提供逐词置信度**，统一输出 `confidence = 1.0`，
  因此真实模式下 `min_confidence` 实际拦不住任何东西。
  要真正的置信度门控需换 PaddleOCR。

## 4. 模块边界

| 模块 | 责任 | 不负责 |
| --- | --- | --- |
| `desktop-app` | 任务编辑、人工确认、状态展示、标定 | 发送决策与系统输入 |
| `automation-core` | 状态机、证据判断、失败收敛 | 操作系统 API、OCR 实现、匹配实现 |
| `vision` | 图像预处理、OCR、模板匹配、文字位置与置信度 | 鼠标点击、业务规则 |
| `platform-windows` | 屏幕捕获、焦点、鼠标、键盘、剪贴板 | 姓名匹配、OCR 或模板匹配 |
| `storage` | SQLite、加密、审计、清理策略 | 屏幕或输入操作 |

macOS 将以 `platform-macos` 实现同一组平台端口；自动化核心与视觉层不因平台改变。

**业务流只依赖 trait，不直接调实现**。目前五个端口：`DesktopPlatform`、`LocalOcr`、
`ContactMatcher`、`IconLocator`、`HumanConfirmation`。`IconLocator` 是最后一个加进来的，
它的存在让"图标定位"这件事可以整体替换（换成 OpenCV、换成模板库）而不动调用方——
见 `docs/todo.md` T9。

## 5. Windows MVP 状态机

**19 个状态**，但**不是一条直线**：同一个状态机要承载三条工作流
（`RunnerConfig.workflow` 决定走哪条），三条在 `WaitingForClient` 之后分岔。

```text
Draft
  → LaunchingClient           （接管已登录的客户端：定位窗口并带到前台，不启动它）
  → WaitingForClient
  → NavigatingToView          （可选：用模板匹配点左侧导航图标，把视图切过去）
  → …                         （三条路在此分岔，见下）
  → Completed | Prepared | Navigated

任意状态 → NeedsHumanReview | Failed | Cancelled
```

三条工作流各自的路径：

```text
① NavigateOnly（工作流 1 / 2「只做导航」）
   WaitingForClient → NavigatingToView → Navigated

② SearchContact（工作流 3 搜索式）
   WaitingForClient → SearchingContact → VerifyingCandidate → VerifyingProfile
                    → OpeningChatFromProfile → VerifyingChatHeader
                    → PreparingMessage → Prepared

③ ScrollListContact（列表扫描式，原有那条）
   WaitingForClient → SearchingContact → VerifyingCandidate
                    → VerifyingChatHeader
                    → PreparingMessage → AwaitingHumanConfirmation
                    → Sending → VerifyingDelivery → Completed
```

两条捷径，都是刻意的：

```text
WaitingForClient → SearchingContact   （关掉「先点击导航图标跳转」时直连，跳过 NavigatingToView）
PreparingMessage → Prepared           （「只填不发」：正文已入框，未发送）
```

⚠️ **`VerifyingCandidate` 有两个出口，不是冗余**：两条路点完人之后落在**不同的页面**。
搜索式点的是搜索下拉里那一行，落到**资料页**（还要再点一次「发消息」）；
列表扫描式点的是会话列表里那一行，**直接进聊天页**。状态机把这个差异显式化了，
而不是让两条路共用一个"打开聊天"状态——那样一旦走错路，
现象是"在资料页上找聊天区标题"，报出来的错会指向完全错误的方向。

关键约束：

- 进入 `Sending` 前，联系人搜索结果与聊天页标题均须与目标名称精确匹配；
- `AwaitingHumanConfirmation` 仅接受当前操作者在界面中的一次明确确认，确认有短时有效期；
- `VerifyingDelivery` 只验证“本次消息内容出现在当前已核验聊天区”，不把网络送达当作可保证的结果；
- 超时、失焦、窗口被替换、OCR 结果冲突、风控或登录界面出现时，转 `NeedsHumanReview`。

### 两条"正常结束但没发送"的路

`Prepared`（「只填不发」，或搜索式工作流）与 `Navigated`（「只做导航」）
都和 `Completed` 一样是**正常结束**，不是失败：

- 它们只能从固定的前驱到达（`PreparingMessage` / `NavigatingToView`），
  **不**属于 `NeedsHumanReview | Failed | Cancelled` 那种任意状态都能跳过去的失败终态；
- 它们不申请发送台账、不写消息摘要、不做送达核验——审计里不该留下任何"像发过了"的痕迹；
- 它们是终态，因此从 `Prepared` 出发再也转不到 `Sending`。这是"只填不发"的安全底线。

⚠️ **搜索式工作流目前无条件停在 `Prepared`**，这是**刻意的**：
操作者要求"发送动作先不要点，mock 上，全部测试通过了再加这个发送逻辑"。
要接发送时，把 `prepare_message` 里那个 `|| search_workflow` 去掉即可，
后面的发送路径与列表式共用，已被用例覆盖过（见 `docs/todo.md` T16）。

### 切换视图：图标上没有文字，只能靠模板匹配

`NavigatingToView` 是可选的一步（`RunnerConfig.navigate_before_search`，**默认关**）：
客户端停在哪个视图，决定了后面那次联系人列表识别到底在看什么。切视图这件事
OCR 完全无能为力——**导航图标上没有任何文字**——所以它走的是另一条路：模板匹配。
它同时是「只做导航」那条工作流（①）的**全部内容**：找图标 → 点它 → `Navigated`。

- 搜索区是**标定过的局部区域**（`nav_strip`，默认窗口宽 7.5% × 整高），
  不是整窗。传整窗的话"图标在哪"就没有任何约束了；
- 模板**由操作者自己截**（界面上「图标库」页，或 `screen_probe template`），
  程序绝不自动裁一块——自动裁会把"点错了地方"变成一次看起来完全正常的运行，
  因为匹配分数照样很高（它匹配的就是它自己刚裁的那块）；
- 同一个图标在**选中 / 未选中 / 带气泡提醒 / 气泡里数字不一样**时长得都不一样，
  所以一个图标名底下可以有**多张图**（`nav_icon_templates` 存的是名字，
  载入时展开成那个名字下的全部图），逐张匹配取最高分；
- 分数低于 `nav_icon_min_score`（默认 0.80）⇒ 转 `NeedsHumanReview`，
  **绝不在低分时"挑一个最像的"点下去**；
- 点击**之后**要比对联系人候选区的画面指纹，没变化就**在证据里留一条警告**。
  这里刻意**不**直接转人工：「画面没变」有两种成因，而在画面上分不出来——
  界面本来就已经停在这个视图上（上一次运行点完就留在这里了，此时点击无效是**正确**行为），
  或者客户端卡死 / 图标被挡住 / 匹配到了不响应点击的位置（此时点击真的没生效）。
  在这一步武断失败，前者就会变成"第二次跑必然失败"，报错文案还会把人引向排查客户端。
  判定交给下一步：`locate_contact` 是只读的，视图不对它就在候选区里找不到目标，
  照样转人工——判据落在能真正决断的地方，而不是在这里猜。
  那一条警告的作用是：真出问题时，日志里已经写明了"视图可能根本没切过去"；
- 缺模板、比例非法、模板尺寸不可用，一律在**装配期**报错（在登记任务之前返回），
  不留一条跑到一半才发现没模板的记录。演练模式同样要求配模板——
  两个模式的校验规则必须一致，否则"演练通过、真实报错"迟早会发生。

判据仍然只有一处：编排层不自己判断"分数够不够"，一律问 `IconLocator::locate`。
`probe_nav_icon` 这个只读命令是唯一的例外，它刻意绕过阈值把**分数本身**报给界面——
标定需要看到分数，而不是一个"过/不过"的结论。

### 客户端由操作者启动，程序只负责"接管"

`LaunchingClient` 这个名字保留（审计记录已按该字符串落库），但它的**语义是接管而非启动**：

- 客户端（微信 / 企业微信）由操作者**自己启动并登录**。扫码、验证码、风控提示
  这些环节一律不进自动化流程——这正是"人工确认不可绕过"在启动阶段的表现；
- `RunnerConfig.launch_wecom` **不属于任务流程**。界面上仍有一个显式的「启动客户端」按钮
  供操作者一键拉起，但它只是便利功能，不在 `execute()` 的路径上；
- 接管 = `focus_wecom()` 找到可见的目标窗口并带到前台。找不到就报 `NeedsHumanReview`，
  文案直接要求"请先手动启动并登录客户端"，不做任何自动拉起或重试。

### 标定尺寸：不一致就自动调回去，调不动才转人工

任务只在标定时的窗口尺寸下运行。尺寸对不上时**先把窗口调回标定尺寸**；
客户端的最小尺寸不允许时**才**转人工，**绝不按错的尺寸去点**。

- 标定值 `CalibratedWindow { width, height, scale_factor }` 由界面的「记录窗口尺寸」
  按钮写入配置（`record_window_geometry`），随 `RunnerConfig.calibrated_window` 持久化；
- 接管窗口后立刻用 `screen_metrics()` 比对，容差为 `WINDOW_SIZE_TOLERANCE_PX = 1`
  与 `SCALE_FACTOR_TOLERANCE = 0.01`；
- **只校验尺寸与 DPI，不校验位置**：区域是相对窗口的比例，运行之间把窗口挪到哪里都无所谓，
  真正会让标定失准的是尺寸变化；
- 尺寸不符、缩放一致 ⇒ 调 `resize_wecom()` 把窗口设回标定尺寸
  （`SetWindowPos` + `SWP_NOMOVE | SWP_NOZORDER | SWP_NOACTIVATE`：只改尺寸，
  不挪位置、不改 Z 序、不抢前台）；
- **判据是调完重新量出来的尺寸，不是请求值**。客户端有自己的最小尺寸限制，
  请求值会被应用夹住而 `SetWindowPos` 照样报成功——量不中就转人工，
  并把「标定 / 调整前 / 调整后」三个尺寸都写进失败原因；
- **缩放不一致时不尝试调整**：DPI 是显示器/系统属性，不是窗口属性。缩放不同意味着
  同一物理尺寸下的逻辑布局本来就不同，调物理像素解决不了，只会白动一次窗口；
- 真实模式在 `build_runner` 阶段就要求 `calibrated_window` 已存在——在**登记任务之前**返回，
  不留下半截任务记录；演练模式则强制置空，避免用替身尺寸去校验真实窗口。

> 为什么容差是 1 像素而不是 0：窗口尺寸经 DPI 缩放换算后可能出现 ±1 的取整差异，
> 卡到 0 会让正常环境随机失败。而 1 像素的偏差对区域定位毫无影响。

> 为什么"自动调"不违反「不确定即失败」：窗口尺寸是程序**完全能确定**的量
> （标定记录里就写着目标值），调它是确定性的、可逆的，不涉及任何对业务内容的猜测。
> 停下让操作者手工拖窗口，只是把一件机器能做的事推给人做。
>
> ⚠️ 调整后**没有**等客户端重排完再截第一帧。理由是窗口是原生 Qt 程序、`WM_SIZE`
> 之后同步重排，而第一次截图还在「点搜索框 + 逐字输入」之后，中间隔着好几次平台调用。
> 若真机上出现"第一帧是半画的"症状，就在这里补一次两帧一致的等待
> （复用 `wait_for_settle` 的判据）。见 `docs/todo.md` T2。

### 滚动查找的边界

`SearchingContact` 是全流程里**唯一一个"反复动作直到成功"的环节**，边界设得最紧。

**多轮扫描（`max_search_sweeps`，默认 2）**。新消息会把目标联系人顶到列表**上方**，
只向下扫一遍会漏。因此：

1. **第一轮刻意不回顶**——从当前位置往下扫是最省的，而"目标在当前位置上方"由第二轮兜住；
2. **第二轮从顶部重扫**，两轮合起来覆盖整张表；
3. 回顶靠"向上滚到画面不再变化"，循环上限是 `max_scroll_attempts + 1`
   （多出的那一次是"空滚"，用来确认真的到顶了——恰好在顶部时不能靠滚动次数判断）。

**单轮内的三重限制**：

1. 滚动次数有上限（`max_scroll_attempts`，默认 20）；
2. 面板截图指纹与上一次相同 ⇒ 不再往下滚，提前收工；
3. 取消令牌每轮都检查，每轮重置单步计时（否则滚 20 次必然撑爆一次 `step_timeout`）。

**"画面没动"要分两种情况**——这是最容易误报的地方：

- **列表到头**：向下滚不动了，但**向上滚一下画面会变** ⇒ 正常收工，继续下一轮扫描；
- **客户端卡死**：正反两个方向都滚不动 ⇒ 转 `NeedsHumanReview`。

判据由两层构成：画面变化（滚完前后截图指纹比对）+ 系统级 `is_responsive()`
（Windows 侧实现为 `IsHungAppWindow`，窗口线程超过 5 秒未取消息即判定未响应）。
系统级判据能抓到"界面还在刷新但主线程已经死锁"之外的另一种情形——
纯粹的画面比对在"滚动恰好滚到一段空白区域"时也会误判。
`RunnerConfig.liveness_check`（默认开）只建议在排查误报时临时关闭。

**歧义不滚动重试**：滚动改变的是"现在能看到谁"，不改变"这个名字是否唯一"。
出现多个逐字匹配时立刻失败，滚下去只会把同一个歧义重复 N 次。

每一轮滚动后都必须**重新截图识别**——滚动会让列表内容整体位移，
上一轮的文字框坐标全部作废，绝不能拿旧结果去点击。

### 卡死判据插在哪些动作前

"卡死"的后果是"看起来操作成功了，其实什么都没发生"，所以它在**每个会产生副作用的动作前**
都要过一遍：点击联系人前、粘贴正文前、发送前。此外：

- 点击联系人**前后各截一次对话区**并比对指纹。指纹不变 ⇒ 提示"点击可能没生效"；
  变化了但标题仍不符 ⇒ 是选错了人。两种情况的排查方向完全不同，必须分开报，
  否则会把操作者引向错误的方向。

## 6. 视觉定位策略

1. 优先使用经过标定的局部区域，不扫描整屏；
2. 对联系人候选区和聊天标题区进行独立 OCR；
3. OCR 输出需包含文字、边界框、置信度和截图指纹；
4. 姓名匹配默认逐字精确匹配；别名规则必须由企业管理员显式配置；
5. 目标坐标在点击前重新计算，并要求窗口、分辨率、缩放比例与当前标定一致；
6. 低置信度、多个精确匹配或文字框过于接近时，拒绝点击。

### 文字之外：模板匹配

OCR 只能回答"这里写了什么"，回答不了"这个图标是什么"。因此当定位目标**没有文字**时
（目前只有导航图标一处），走模板匹配，判据是归一化互相关系数（NCC，等价于
OpenCV 的 `TM_CCOEFF_NORMED`）：

- 逐通道计算再取平均。只比灰度会丢掉色相——两块"通道均值完全相同、只有色相不同"
  的图案在灰度下无法区分，而图标恰恰是彩色的；
- 归一化 ⇒ 对**亮度与对比度变化免疫**：窗口失去焦点、主题变暗都不会让分数掉下来。
  差值型度量（`TM_SQDIFF`）在这种场景下会直接失效；
- 对纯色模板、模板比搜索区还大这两种情况返回 `None`（"这里没有可匹配的图案"），
  而不是返回一个 0 分的位置——这两件事的排查方向完全不同；
- 实现放在 `crates/vision`，纯 Rust，不依赖 OpenCV。取舍见 `docs/todo.md` T9。

模板匹配与 OCR 共用同一个约束：**不确定即失败**。分数没过阈值就转人工，
绝不"挑一个最像的"点下去。

#### 位置先验：多个图标长得像时，越靠近导航区中心越可信

左侧导航栏是一列**纵向排列、彼此长得很像**的线性图标。逐张模板取最高分时，
偶尔会出现"旁边那个图标得分略高一点"——而**点错图标的代价是后面整条流程
都作用在错误的视图上**，比直接失败严重得多。

可用的先验信息是：**越靠近导航区中心的命中越可信**。导航区是一列窄带，
图标都排在它的纵向中心线附近；离中心很远的命中多半是列表里的头像、
未读红点这类"看起来也像个小方块"的东西。

⚠️ **但先验绝不能把低分命中抬上来。** 只用"离中心最近"会引入一个更坏的缺陷：
一个 0.82 分的噪声命中恰好压在中心上，就能把 0.99 分的正确命中挤掉。
所以设计成两段：

1. **先按分数定阈值** —— 没过 `min_score` 就直接转人工，先验根本不参与；
2. **再在"分数本来就相近"的候选里比距离** —— 只有分数不低于
   「最高分 − `score_tolerance`」的候选才有资格比位置。

容差取 0 等于关掉先验（只有并列最高分才会看位置）。
平局规则是三级、且**确定性**的：距离 → 分数 → `(y, x)` 取最小，
保证同一个输入永远给同一个答案（否则用例会变成概率性的）。

先验只在**导航图标**这一处启用。列表扫描式、搜索式的定位都是"读文字"，
文字本身就把目标唯一确定了，不存在"两个候选长得像"的问题。

#### 模板从哪来：图标库

模板**只能由人从真实画面上框出来**，程序绝不自己裁一块"看起来像图标"的区域：
猜错位置、裁到空白，都会变成一次**静默的、看起来完全正常**的运行——
匹配分数照样很高（它匹配的就是它自己刚裁的那块），点击照样发出去，
只是点到了别的地方。

所以界面上有一页「图标库」：截一张窗口画面 → 在图上框住图标 → 起个名字存下来。
**一个名字对应一个目录**（`<图标库>/<名字>/1.png`、`2.png`…），目录里可以放多张图：
同一个图标在选中 / 未选中 / 带气泡时长得不一样，而它们指的是同一个图标。
配置里引用的也是**名字**，载入时才展开成"这个名字下的全部图"——
这样以后补一张变体不必回配置页重勾一次，而漏勾是不会报错的，只会表现为
"某个状态下匹配不上"。

图标库默认在**数据目录**下的 `icons/`（可在界面上改，`RuntimeConfig.icons_dir`）：
模板是人对着屏幕一张一张框出来的素材，与配置、日志、证据图放在一处才好找、好备份。
名字会被拼成**目录名**，因此校验很严（不允许路径分隔符、结尾的点、
Windows 保留设备名）——判据只有一处，见 `docs/windows-mvp-interface.md`。

**框选之后要回到原始分辨率重截一张**，不能从预览图上裁：预览是缩放过的，
裁出来的模板边缘会带上插值杂色，拿去匹配真实画面自然对不准，而且分数不会低到
让人起疑。代价是必须确认两次截图之间窗口尺寸没变，变了就直接拒绝并要求重截。

### 运行期数据放在哪

**程序运行当前路径**下的 `data/`。规则只有一处定义：`src-tauri/src/data_dir.rs`
（`working_dir()/data`），图标库的默认位置也从那儿取。

装的是：`config.json`、`icons/`、`audit.sqlite`、`evidence/`、`task-<ID前8位>.log`。
放在一处是为了**整个目录可以整体拷走**——这也是不用 AppData 的原因：
那层目录名是包标识符，备份与迁移时得先知道去哪儿找。

⚠️ **「当前路径」是进程的工作目录，不是 exe 所在目录。** 两者在双击时通常一致，
但从别处启动时不同：

```text
C:\> D:\tools\rpa\desktop.exe      ← 工作目录是 C:\，data 会建在 C:\data
```

这是「相对路径」这个词的必然代价，之所以接受它：实际使用的目录**会显示在界面上**
（`RuntimeInfo::data_dir`，见 `RuntimePanel` 底部），路径不对时一眼就能看见，
而不是等到「配置怎么没生效」再来查。

⚠️ **双击 `target\debug\desktop.exe` 时，数据目录是 `target\debug\data\`**，
而 `cargo clean` 会把它一起删掉（标定要重做一遍）。仓库根的 `run.cmd` 先切到
仓库根再启动，就是为了避开这个。

启动时 `data_dir::ensure()` 检查并创建；建不出来**就让启动失败**，不降级、不回退到
别的目录——数据目录是配置、图标库、审计库的唯一落脚点，找不到它时程序没有正确的
工作方式，硬跑下去只会把数据写到用户不知道的地方，而那种问题事后极难查。

**旧版数据会搬一次**：数据目录从 `%APPDATA%\com.example.wecom-local-rpa\` 换过来，
所以 `legacy_data::migrate` 会在**数据目录里还没有 `config.json`** 时，
把旧位置的 `config.json` 与 `icons/` 复制过来（旧目录原样留着，不删）。
搬不动**不阻断启动**，但会在界面上说出来——不说的话，用户看到的是空配置，
会以为数据丢了，而旧文件其实还好好躺在 AppData 里。

## 7. 数据与审计

SQLite 只保存执行任务必需的数据。消息正文默认不长期保存；审计记录存储消息摘要（长度、哈希、时间）而非全文。失败截图须局部裁切并脱敏，设置可配置的自动清理期限。

每条审计记录至少包含：任务 ID、操作者、平台、企业微信版本（若可获得）、状态转换、确认时间、失败代码和证据引用。不得记录剪贴板原文、账号令牌或完整聊天历史。

## 8. 权限与发布

- Windows MVP 仅在交互式已解锁的桌面会话中运行；
- 程序需要明确提示用户：发送期间请勿切换窗口或操作鼠标键盘；
- 后续 macOS 版本首次启动时，需要引导授予“辅助功能”和“屏幕录制”权限；
- 所有构建产物签名发布，模型与依赖清单可追溯。

## 9. MVP 验收条件

Windows 测试设备上，以专用测试账号和测试外部联系人验证：

1. 可定位已打开且前台的企业微信；
2. 能以 OCR 找到唯一的测试联系人并完成双重姓名核验；
3. 操作者确认后才能粘贴与发送一条纯文本消息；
4. 能在聊天区识别到本条消息作为界面完成证据；
5. 出现同名、识别失败、失焦或登录/限制提示时不会发送，并会留下可读失败原因。
