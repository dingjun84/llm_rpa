# 企业微信本地视觉自动化

在**已登录的企业微信桌面客户端**中，用**本地屏幕截图 + 本地 OCR + 鼠标键盘剪贴板**
完成一对一外部联系人的纯文本消息发送。

所有识别与决策都在本机完成：不联网、不注入、不 Hook、不读取客户端内存。
**每一条消息都必须由操作者在界面上确认后才会发出。**

当前支持 **Windows** 与 **macOS**：同一套业务流程，平台适配层分立。

## 安全边界

这几条是硬约束，不是"暂未实现"：

- **本地优先**——图像、OCR、任务数据与审计记录都不出本机；不调用企业微信服务端 API。
- **先验证再动作**——每一次点击、粘贴、发送前都要重新确认前台窗口与标定一致。
- **不确定即失败**——识别冲突、超时、失焦、窗口被替换一律转人工处理，不猜、不重试到成功。
- **人工确认不可绕过**——确认端口只接受界面来的确认，且有短时有效期。
- **消息正文不落库**——审计只存 `char_count` + `sha256` + 时间；证据只存脱敏后的局部截图指纹。
- 不处理验证码/登录异常，不做无人值守批量发送、自动加好友或自动回复。

## 运行模式

| 模式 | 行为 |
| --- | --- |
| **演练模式**（默认） | 全部使用替身端口。不启动企业微信、不产生任何真实输入，可注入故障场景观察收敛结果。 |
| **真实模式** | 操作本机真实窗口。发送期间请勿切换窗口或操作鼠标键盘。**挪动**目标窗口没关系（位置不校验），但**缩放**会被自动调回标定尺寸；调不动（客户端有最小尺寸限制）就转人工。 |

真实模式需要显式配置：企业微信可执行文件路径（可选 SHA-256 校验）、窗口类名、
本地 OCR 程序路径、**四个区域的标定**，以及**标定窗口尺寸**。

### 客户端由你启动并登录

客户端（微信 / 企业微信）**由操作者自己启动并登录**，任务只负责「接管」已经就绪的窗口：
定位到它、带到前台，然后开始干活。程序**不会**自己去拉起客户端。

这样安排是因为自动启动有三个绕不开的麻烦：重复启动会弹出登录窗；登录窗和主窗口
**共用同一个窗口类名**（Qt 系程序都这样），定位时容易选错；以及「还没登录完就被当成就绪」。
扫码、验证码这些环节程序也插不上手。

界面上保留了一个显式的「启动客户端」按钮，按你填的路径拉起程序——但它只是一个便利入口，
不在任务流程里。**登录状态由你自己确认**，程序不会去判断。

### 标定窗口尺寸

点一次「记录窗口尺寸」，把当时的窗口宽高与显示器缩放记下来。之后：

- 任务开始时**只按这个尺寸**运行：尺寸对不上会**先自动把窗口调回这个尺寸**，
  客户端的最小尺寸不允许时**才**转人工，绝不按错的尺寸去点；
- **DPI 对不上不尝试调整**——缩放是显示器属性、不是窗口属性，调物理像素解决不了，
  直接转人工；
- **位置不校验**——区域是相对窗口的比例，运行之间把窗口挪到哪儿都无所谓；
- 真实模式**没有标定尺寸就不让开始**（在登记任务之前就拦下，不留半截任务记录）。

容差是 1 像素与 1% 缩放：DPI 换算会有 ±1 的取整差异，卡到 0 会让正常环境随机失败。

> 调整窗口用的是 `SetWindowPos` + `SWP_NOMOVE | SWP_NOZORDER | SWP_NOACTIVATE`：
> 只改尺寸，不挪位置、不改层级、不抢前台。判据是**调完重新量出来的**尺寸——
> 客户端会用自己的最小尺寸把请求值夹住，而 `SetWindowPos` 照样报成功。
> 想**换一个**窗口尺寸，就得重标区域 + 重记尺寸，见 `docs/todo.md` T2。

### 卡死检测

客户端假死时最危险的不是报错，而是**看起来操作成功了、其实什么都没发生**。所以每个
会产生副作用的动作（点击、粘贴、**发送**）之前都要过一次检测，两条判据互补：

- **画面变化**：滚一下，看画面有没有变；
- **系统级**：`IsHungAppWindow`——窗口所属线程超过 5 秒没取消息就判定未响应。

这里有个必须分开的情况：**「画面没动」有两种含义**。列表**滚到底**了是正常收工，
程序**卡死**了必须转人工。判据是**反向滚一下**——反方向能改变画面就是到底了，
正反都不动才是卡死。少了这一步，「联系人少、一屏就到底」会被误报成卡死。

界面上有「卡死检测」开关（默认开），**只建议在排查误报时临时关掉**。

### 只填不发

真实模式下的一个独立开关。打开后流程走到「准备消息」就结束：
**定位联系人 → 点进输入框 → 填入正文 → 停**，绝不发送。

用途是验证「能不能滚到目标、能不能点准、文字有没有进对地方」，
而不会给对方造成任何影响。它在**演练模式下同样可用**，
可以先用替身把逻辑跑通再上真机。

这一模式下任务终态是 `Prepared`（已填入正文，未发送）——它是**正常结束**，
不是失败。它不会申请发送台账、不写消息摘要、不做送达核验，
审计里不会留下任何「像发过了」的痕迹；而且 `Prepared` 是终态，
从它出发再也转不到 `Sending`。

### 滚动查找联系人

联系人不在当前可见范围时，会在联系人候选区滚动继续找。**扫两轮**：

1. 第一轮从当前位置**向下**扫（刻意不先回顶——从当前位置往下最省）；
2. 第二轮**回到顶部重扫**。

为什么要两轮：列表按「最近有消息」排序，扫描期间到达的新消息会把目标**顶到列表上方**，
而那一屏早就被翻过去了——只往下扫一遍就会漏。

单轮内的边界：

- 滚动次数有上限（默认 20 次）；
- 画面不再变化 ⇒ 滚到底了，提前收工，不做无谓重复；
- 每轮都检查取消令牌，每轮重置单步计时（否则滚 20 次必然撑爆一次单步超时）。

两轮扫完仍未找到，或出现**同名/过于接近的候选**，任务转人工处理。
同名的情况**不滚动重试**——滚动改变的是「现在能看到谁」，
不改变「这个名字是否唯一」，滚下去只会把同一个歧义重复 N 次。

「完整扫描轮数」配成 1 就退回「只往下扫一遍」的老行为。

点击联系人之后还会**前后各截一次对话区比对**：画面没变说明点击可能没生效，
变了但标题对不上说明是选错了人——这两种情况的排查方向完全不同，界面会分开提示。

## 区域标定

真实模式依赖若干**相对窗口的比例区域**（窗口挪动、换分辨率都不必重标）：
会话列表区、聊天页标题与正文、消息输入框，以及搜索式工作流要用的顶部搜索框、
联想下拉、联系人资料区、左侧导航区。

默认值是照企业微信界面猜的，**不同版本、窗口尺寸、DPI 下都必须重标**。
在**「界面标定」页**按场景（主界面 / 历史对话 / 联系人列表 / 搜索下拉列表）
切到对应界面、截图、把每一块框出来——清单只有后端一份（`calibration/catalog.rs`），
界面按它渲染。预览是纯只读的：不点击、不粘贴、不发送，也不会把目标窗口抢到前台。

> 「任务」页上原来还有一份"手填百分比"的区域标定面板，已经删掉：它和「界面标定」页
> 改的是同一份配置，两处并存只会让人不知道该信哪一边。

## 本地 OCR

`tools/winocr` 是一个**本仓库自己的**可执行文件：从 stdin 收 PNG、调 Windows 自带的
`Windows.Media.Ocr`、把 JSON 数组写到 stdout。完全离线、不装第三方模型。

⚠️ **系统自带的是那个 OCR 引擎，不是这个 exe。** `winocr.exe` 得自己构建，而且
**必须单独构建**——它不是 `desktop` 的依赖：

```bash
CARGO_INCREMENTAL=0 cargo build -p winocr
```

漏了这一步的症状很能骗人：程序照常打开、任务也点得动，一直到第一次识别才报
「本地 OCR 进程启动失败：…\target\debug\winocr.exe：系统找不到指定的文件」。
（`cargo test --workspace` 也**不会**生成它，只会在 `target\debug\deps\` 下留一个
带哈希的副本。）构建后把路径填进配置：

```jsonc
"ocr_command": "<仓库>/target/debug/winocr.exe"
```

已知限制：该引擎对中文按字切词（工具内已做 CJK 空格归并），
且**不提供逐词置信度**，统一输出 `confidence = 1.0`——
所以真实模式下 `min_confidence` 拦不住东西。要真正的置信度门控需换 PaddleOCR。

## macOS 设置

1. **系统设置 → 隐私与安全性**：为本应用（或启动它的终端）打开 **屏幕录制** 与 **辅助功能**，然后重启应用。
2. 用界面「指认窗口」写入所有者名（应用显示名）与 `.app` 路径；Mac 上配置里的「窗口类名」表示所有者名，不是 Win32 类名。
3. 编译本地 OCR：

```bash
cd tools/macosocr
swiftc -O -framework Vision -framework CoreGraphics \
  -o ../../target/debug/macosocr macosocr.swift
```

把得到的路径填进配置的 `ocr_command`。

更完整的说明见 [`docs/macos.md`](docs/macos.md)。

## 构建与测试

```bash
# CARGO_INCREMENTAL=0 是默认动作：本机反复蓝屏会留下"内容错但元数据正常"的产物，
# 增量缓存复用它们会让报错指向跟真因无关的 crate。
CARGO_INCREMENTAL=0 cargo test --workspace

# 要「双击就能跑」必须带 custom-protocol：不带它构建会被判定为 dev，
# 前端资源根本不嵌进 exe，双击得到白窗口。
CARGO_INCREMENTAL=0 cargo build -p desktop --features custom-protocol

# 本地 OCR 程序。**必须单独建**：它不是 desktop 的依赖，
# `cargo build -p desktop` 不会建它；`cargo test --workspace` 也只在
# target\debug\deps\ 下留一个带哈希的副本，不生成 target\debug\winocr.exe。
CARGO_INCREMENTAL=0 cargo build -p winocr

cd apps/desktop && npm install && npm run build   # 前端产物（改了前端后必须重跑，再重新 cargo build）
cd apps/desktop && npm run tauri dev              # 开发模式（靠 dev 服务器供页面）
```

> 改了 `.tsx`/`.ts`/`.css` 之后：先 `npm run build` 再 `cargo build`。
> `tsc --noEmit` 只做类型检查、**不产出 `dist/`**，跳过 `npm run build` 会把上一版
> 前端资源嵌进 exe，而 `cargo build` 照样成功、不报任何错。

实机诊断工具（本机没装企业微信时，可拿任意窗口验证平台层）：

```bash
CARGO_INCREMENTAL=0 cargo build -p platform-windows --example screen_probe
screen_probe list                                    # 列出窗口
screen_probe capture "<匹配串>" out.png               # 整窗截屏
screen_probe pick                                    # 读光标下的窗口（类名/标题/exe）
screen_probe focus <窗口类名> [exe路径]                # 只验证「能不能接管窗口」
screen_probe type "<匹配串>" <x> <y> "文本"            # 聚焦并输入（窗口相对坐标）
```

给「先点击导航图标跳转」标定用（模板必须**自己框**，别让程序自动裁）：

**日常用界面**：打开程序 → 顶部「图标库」页 →

1. 点「截取窗口画面」（只读，不点击、不聚焦）；
2. 在图上**按住左键拖出一个框**，框住那个图标（框大了会带一圈背景，分数就低）；
3. 起个名字（例如「通讯录」）→「保存到图标库」；
4. 点「测试匹配」看分数 —— 绿框过阈值、红框没过，**红框也要看**，
   它标的是「它认为最像的地方」，那个位置对不对才是判断模板对不对的依据；
5. 点「定位并点击」**真的试一下**（两次点击确认，第二次才真的点）；
6. 勾上「用于导航」+ 打开「任务开始前先点击导航图标跳转」→ 点「保存配置」。

图标存在 `<数据目录>/icons/<名字>.png`，界面会显示这个目录。

命令行探针（**排查用**，不是日常路径）：

```bash
screen_probe template "<匹配串>" nav.png 0 120 26 26   # 从窗口裁出图标模板存 PNG
screen_probe findicon "<匹配串>" nav.png              # 量一次分数与位置（只读，不点击）
```

> 导航图标上没有文字，OCR 读不到它，所以「先切到联系人视图」这一步只能靠模板匹配。
> 同一个图标在**选中 / 未选中**两种状态下长得不一样，建议各存一张、名字区分开——
> 否则会出现"上一次点完停在这个页面上，这一次再也匹配不上"。
>
> ⚠️ 用命令行的 `template` 截出来的 PNG 要**自己放进图标库目录**才会出现在界面列表里；
> 界面里的「截取」走的是另一条路（按框重新截一张原始分辨率的画面），
> 因为预览图是缩放过的，从它上面裁出来的模板对不准。

真实模式的手动验收（需要目标窗口在前台，因此要在你自己的交互式会话里跑）：

```bash
cargo test -p desktop --test live_smoke -- --ignored --nocapture
```
